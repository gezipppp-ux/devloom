## 共通的功能重组

1. 日常业务入口与管理入口分开。顶层保留“项目 / 我的工作”，管理员功能收进“管理中心”，个人设置及退出收进头像菜单。
2. 需求与 Bug 合并到“事项”，用类型筛选与图标区分，保留各自的流程与字段。详情以单独页面或侧抽屉展开，列表上下文保持。
3. 开发任务与执行准备组成连续流程：选择范围 → 认领／指派 → 检查环境与分支 → 明确开始开发。允许在同一页面完成，认领仍不隐式启动 Agent。
4. 开发工作台默认专注会话；代码、Git、关联事项和运行细节按需打开。执行审批直接靠近当前内容呈现。业务进度与 Agent 运行状态分别显示。
5. 版本范围、公开交付结果与验收入口聚合到“交付”，不引入未实现的云部署／自动发布语义。AI 返回结果不代表业务验收通过。
6. 成员分工、提示词与项目配置收进“项目设置”；资料库汇总资产与附件，敏感字段仍独立授权。
7. 登录和初始化仍独立。高级配置渐进展开，缺少 Git／权限／环境时给出当前步骤内的解决入口与返回位置。

## A · 项目工作台

适合：项目协作和权限分工明确的团队；最接近现有数据组织，改造风险较低。

导航：项目 / 我的工作；项目内：事项 / 开发 / 交付 / 资料。项目设置在右上角。管理员入口放头像菜单。

四页：①项目首页 → ②统一事项列表 → ③开发任务及准备 → ④专注 AI 工作台。

页面要点：项目首页只放项目与最近访问；事项统一筛选，保留需求和缺陷类型；开发页把任务范围、个人空间与分支选择放在一次连续操作里；会话页收起代码与历史列表。

跨页面流程：进入项目 → 查看／创建事项 → 认领或指派 → 任务准备（可合并本人同版本任务）→ 显式启动 → 会话与交付。

## B · 我的工作台

适合：开发者日常高频使用、多项目切换；突出“接下来做什么”。

导航：我的工作 / 项目 / 资料；单一窄侧导航，无第二列常驻任务列表。

四页：①我的工作 → ②事项详情与认领 → ③开始开发向导 → ④开发会话与交付预览。

页面要点：首页按“待我处理 / 开发中 / 待验收”显示少量任务；详情兼容需求与缺陷；启动向导把 Git、环境、分支、执行设置串起来；会话页用“对话 / 变更 / 交付”切换，避免同时堆出所有信息。

跨页面流程：打开本人待办 → 阅读详情并认领 → 在向导准备执行 → 对话开发 → 发布交付记录并交给有权限的人验收。

新增设计需求：跨项目个人任务聚合、可见范围内的待验收聚合、最近访问。这些是提案，当前前端没有统一聚合页，需要对应 API 或聚合层支持；“我的工作”不包含其他成员的私有会话。

## C · 版本交付空间

适合：以迭代版本组织需求与协作的团队；强调范围、执行、验收的衔接。

导航：项目 → 选定版本；版本内：范围 / 执行 / 验收 / 资料。未排期事项保留入口，独立开发仍可从开发入口进入。

四页：①项目与版本首页 → ②版本范围规划 → ③版本关联开发工作台 → ④验收与归档。

页面要点：项目首页提供版本入口；范围规划把需求和缺陷放在同一清单；执行页聚焦本人的开发任务及会话；验收页聚合已存在的事项状态和公开交付记录，展示归档前的未完成项。

跨页面流程：选择项目和目标版本 → 确认范围 → 分配并规划任务 → 明确开始执行 → 提交公开交付 → 验收事项 → 满足门禁后归档版本。

新增设计需求：版本范围与交付的聚合视图、归档阻塞项汇总；基于当前版本／事项／任务数据重组，需实现聚合查询。此处“交付”不表示向生产环境部署。

## 设置与低频页面的归属

| 当前分散入口 | 建议归属 |
| --- | --- |
| 部门可用功能、账号管理 | 管理中心 / 组织与权限 |
| Agent 供应商、环境检测、成员目录 | 管理中心 / 运行平台 |
| 需求／Bug 流程编排 | 管理中心 / 事项流程 |
| 初始化记录 | 管理中心 / 系统记录 |
| Git、MCP、默认模型／权限、通知、安全 | 个人中心，分组页面 |
| 成员、提示词、项目配置 | 项目设置 |
| 文档、附件、环境地址、受保护凭据 | 项目资料库，保留权限差异 |

## 实现时保持的业务边界

- 部门功能上限、项目分工及个人所有者边界继续生效。管理员并不自动获得其他成员的代码与会话访问权。
- UI 可以重组操作路径，但认领、环境准备和启动执行仍是独立业务动作，最终启动必须明确。
- 需求／Bug 的业务状态、开发任务状态、Agent 运行状态独立。任务完成或 Agent 返回不自动代表验收通过。
- 同版本本人未启动任务才可合并；归档版本保留现有业务门禁。保留现有会话、分支及工作目录身份。

## 图像交付

每套方案以 2×2 排版展示四张完整页面；原始页面另存 pages/，便于放大检查。三套分别比较信息架构与操作路径，不只是换配色。推荐先比较 A 与 B，版本驱动的团队再优先考虑 C。
