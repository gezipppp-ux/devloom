# DevLoom UI 实施

设计依据为 [UI 重构 PRD](../../../docs/prd/ui-refactor.md)、[页面映射](../../../docs/prd/ui-refactor-pages.md) 与 [neutral-workbench](../neutral-workbench/SKILL.md)。B 方案是通用视觉基线，具体功能的布局与交互沿用用户后续确认的方案，例如[事项与流程操作 A 方案](../../../docs/prototypes/ui-refactor/workflow-actions/README.md)。旧 UI skills 不作为视觉、布局或交互依据。

## 先确认任务阶段

- 原型阶段：编辑 `docs/prototypes/ui-refactor/`、PRD 和 skills，使用模拟数据；HTML 可直接打开且不依赖生产 API。
- Vue 实施阶段：用户确认原型后才进入。先读取 [工程规范](../web-coding-engineering/SKILL.md)、[账号与数据库契约](../../../docs/engineering/accounts-and-database.md) 和受影响功能的真实接口。不能把效果图里的字段和模型名当成 API 契约。
- 目前阶段记录在 PRD；当前请求若已包含后续实施授权，不再重复询问。否则不从“完善原型”推断出全量替换授权。

## 新增交互先设计整页

新增按钮、表单、工具栏、面板或改变布局时，即使功能很小，也先查看现有完整页面和已确认方案，再确定新增内容的位置。纯文案或数据绑定修复无需额外制作原型；文案长度影响布局时仍检查受影响页面。

实施前用简短说明、草图或已有 PRD 记录以下决定，形式按改动规模选择，无需为普通迭代新建一套设计文档：

- 用户在此页面要完成什么，最主要的下一步是什么。
- 主操作、次操作和低频操作分别放在哪里；哪些既有入口需要合并、收纳或移动。
- 新内容与正文、表单、画布等主体怎样分配空间，窄屏怎样重排。
- 复用哪些现有组件和状态呈现方式，哪些真实数据或状态最容易破坏布局。

沿用已确认方向与共享组件，在已授权范围内直接实施。用户要求比较方案，或整体交互方向确实需要选择时才提供多方案；不固定要求三套，不把每次新增交互变成重新审批。若新增内容造成拥挤，应调整受影响区域的组织方式，不按后端接口数量逐个堆放按钮，也不借机重做无关页面。

## 页面与实现

- 导航按工作对象组织，统一工作台／项目／事项／开发／交付；不按产品经理或研发身份生成壳层。
- 响应式和颜色采用 [新设计变量](../neutral-workbench/assets/tokens.css)。原型不导入生产旧 CSS。正式实施时把已确认变量纳入生产共享主题，并同步组件库；不要永久维护两套冲突变量。
- 表单、列表、详情、抽屉和会话使用共享的视觉基础；业务字段、授权及状态由对应功能负责。Vue 继续遵守 `main.js → app → features → shared`，跨功能由 app 组合。
- 界面支持简体中文／英文，复用 `shared/i18n` 和 `LocaleSelect`。动态句子使用命名插值，日期／数字使用 locale 格式化；切换保留草稿和对象身份。用户正文、代码、提示词与自定义流程名称不作为 UI 文案翻译。检查英文长文案在窄屏的换行和可访问名称。
- 新设计允许调整导航和交互顺序，但保留对象身份与深链映射。请求按账号／项目／任务隔离，迟到响应不能污染新上下文；切换和卸载释放订阅。
- 动作必须有可见结果，输入失败保留草稿。浏览、准备、保存、执行分别表达，不把每个动作都处理为通用成功消息。
- 界面文案围绕用户动作和结果组织。只保留影响当前决策的说明；实现细节、配置教程放入帮助或按需展开区域。影响范围、必填条件和操作错误仍靠近对应动作，不能为减少文字而隐藏。
- 新增跨项目聚合、搜索、交付队列时先明确后端查询和权限策略；原型可以演示，但不能声称接口已实现。

## 不可改变的业务边界

事项状态、开发任务状态和 Agent 运行状态独立。认领／分派／合并不执行 Agent，开始开发需要明确提交；开始结果未知时查询原请求。仅执行者能访问本人会话和代码，发布交付时明确共享范围。已归档对象只读，清理文件与删除历史需明确影响并保留真实身份。

## 验证

原型检查真实交互、语法、链接、无外部调用，以及 1920×1080／2560×1440／1440×900／1280×720／768×1024／390×844／320×740 布局；特别检查长内容、详情、会话、确认窗与表单底部。截图放在忽略的 `state/`，不能拿图片缩放代替 CSS 视口验证。

生产实现按仓库 AGENTS 与 Jenkins 执行 lint、架构／单元／集成、构建和浏览器回归。原型审阅不能代替生产权限、并发与执行测试。提交前说明当前交付阶段和仍需用户确认的范围。

功能验收和视觉验收分别完成。新增交互或布局变化必须查看实际页面截图，不能以测试通过、组件单独好看或没有横向溢出代替整页审查：

- 在上述真实 CSS 视口检查受影响的完整页面和展开后的表单／弹窗；布局调整尽量保留相同视口的前后对照。原型阶段检查原型，正式实施检查实际应用。
- 使用符合真实字段长度和数量的模拟数据，覆盖长标题、多项可用操作，以及受影响的空、失败、禁用／只读状态；检查中英文。不得为了截图修改生产业务数据。
- 按 [neutral-workbench 的验收标准](../neutral-workbench/SKILL.md#验收) 检查操作主次、信息密度、重复内容、对齐留白和相邻页面的一致性。发现问题后调整并复查受影响页面，不用孤立控件截图代替整页效果。
- 交付说明分别列出功能与视觉检查结果，并提供可访问的截图或截图目录；如受环境限制未完成视觉检查，明确记录缺口，不声称已通过 UI 验收。
