# DevLoom 需求与 Bug 提报

把口头想法、运营反馈、技术方案和故障现象整理成研发可以实施、测试可以验证、业务可以验收的事项。适用于产品经理、运营人员和研发；不按岗位降低质量标准，也不要求提报人掌握技术术语。

本技能的门禁由 Agent 在发布前执行，不代表 MCP 服务端已经强制校验这些内容。技能可以独立使用，不依赖另一个本地 skill。创建技能、写草稿、检查质量均不等于发布事项。

## 三条必守规则

1. **需求涉及页面改动，必须有原型附件。** 原型图、可读取的原型文件或包含入口与依赖的压缩包，至少提供一种。必须实际读取并与需求核对，发布时正式绑定附件。仅有文字、不可访问链接、现状截图、文件名或“后续补图”不算满足要求。
2. **新需求必须边界明确、逻辑自洽、具备实施条件和可验证的验收标准。** 未确定的核心规则、相互矛盾的原型与文字、未解决的前置依赖均阻止发布。不得把“待定”“研发自行决定业务规则”写进正式事项来绕过门禁。
3. **新 Bug 必须填写描述、复现步骤、预期结果、实际结果四个独立字段。** 截图可选；已有且与问题相关的截图应读取、引用并绑定。没有截图不阻止内容完整的 Bug；不得虚构截图、复现次数、环境或根因。

## 根据提报材料整理，而不是根据岗位猜测

| 常见材料 | 整理重点 |
| --- | --- |
| 产品目标、流程、原型 | 补齐角色、范围、业务规则、页面状态、异常路径和验收标准 |
| 运营反馈、活动规则、用户案例 | 保留原始场景，明确适用人群、活动时间与时区、规则优先级、次数或额度边界；只处理实际涉及的项目 |
| 技术方案、接口、日志 | 分开业务结果与实现建议，明确输入输出、错误行为、权限、数据兼容性和验证方法 |

以上不是岗位限制。不要要求运营人员提供数据库设计、要求产品经理诊断代码根因，或把研发提出的推测写成已确认业务事实。权限一律以 MCP 返回的账号、Token 和项目权限为准。

## 工作顺序

### 0. 确认连接与技能版本

每轮使用本技能时，按 [安装与更新](references/updating.md) 检查一次。先确定本次使用的 DevLoom MCP 连接，调用 `whoami` 读取 `runtime`、`skills` 和 Token 到期时间；所有站点、更新和上传地址均来自这个连接。未配置 MCP 时使用用户提供的安装清单地址，不猜测服务器地址。

使用 `skills.manifestUrl` 检查并更新完整技能目录，包括 references、agents 和 scripts。校验失败保留当前版本，可继续只读查询和草稿准备，暂缓业务写操作。更新成功后重新读取入口及本次需要的 references。更新技能不等于授权发布事项。

### 1. 判断要做什么

- 明确用户要草拟、审查、创建，还是补充已有事项。只要求整理时输出草稿，不调用写工具。
- 需求是新增或改变已约定的能力；Bug 是可观察的行为偏离已有约定。无预期依据时先找既有需求、原型、文档或产品决定，不能把新愿望当缺陷。
- 一个事项围绕一个可独立验收的目标。混合多个目标时先提出拆分结果；批量发布须在用户授权范围内，不擅自创建一组事项。
- 已知项目、文件、版本、人员和规则从当前对话及可读资料取得，不重复询问。目标项目不明确且无法可靠定位时才请用户选择。

### 2. 查询项目上下文

按 [MCP 发布说明](references/mcp-publishing.md) 验证连接和接口，查询项目、版本、有效成员、对应类型的已发布流程，并查重。没有连接时继续整理本地草稿，说明发布尚缺连接。

遇到相似事项先读取详情，比较目标、触发条件和验收范围；确认相同后引用已有事项。只有用户授权补充或更新时才编辑已有事项；不要自行重复创建、关闭或重开。

### 3. 按类型补齐内容

- **需求：**读取 [需求规范与模板](references/requirements.md)，形成范围、规则编号和验收用例。没有页面变化的接口、数据或后台需求注明“原型不适用”及具体理由。
- **页面需求或包含原型的事项：**另外读取 [原型与附件检查](references/prototypes.md)。页面布局、字段、按钮、文案、交互、可见性或状态反馈变化都属于页面改动；局部变化可以用局部原型。
- **Bug：**读取 [Bug 规范与模板](references/bugs.md)，把四项必填内容映射到实际 MCP 字段。复现步骤可以来自提报人；必须标明是否经过 Agent 验证。

先完成能从资料确认的部分，再集中列出影响实施或验收的缺口。每个问题指出缺失事实、影响和可选决策，提供建议但不擅自采用未确认的核心业务规则。格式、编号、语句整理可以直接完成。

### 4. 执行发布门禁

先检查 G1–G5，逐项输出“通过 / 不适用（原因）/ 阻塞（缺什么）”，以事实和具体文件、规则或验收编号作为依据，不用打分平均掉硬性缺口。G6 在下一步展示完整稿、完成授权与上传后检查，不能因为尚未展示草稿或上传就停止准备工作。

| 门禁 | 通过条件 |
| --- | --- |
| G1 目标与范围 | 类型和目标项目明确，用户、场景、问题和本次范围可识别；查重已完成 |
| G2 内容完整 | 需求规则可实施且无关键待定项；Bug 四项必填真实、具体，预期有依据 |
| G3 原型与证据 | 页面需求有已读取的目标原型，关键状态有说明且图文一致；已提供的相关附件可读取并满足上传约束 |
| G4 验收闭环 | 每条核心规则或缺陷有可执行的验证步骤和客观通过条件；相关异常与边界被覆盖 |
| G5 实施与流程 | 阻塞实施的依赖已解决；已核对发布流程与本次操作所需权限、字段和成员；不把未来交付证据当创建必填项 |
| G6 发布授权与参数 | 完整草稿已经获得适用于本次发布的授权，最终字段与附件一致，无占位符；绑定前所有附件上传成功 |

任一适用的内容门禁阻塞：保留本地或对话草稿，说明“待补充，未发布”，仅追问解除阻塞所需的信息。内容检查通过后继续下一步，但 G6 未完成前不得提交。不先创建一个空壳事项再承诺补齐。这里的“待补充 / 可发布”是工作结论，不是 MCP 状态字段。

### 5. 展示完整发布稿并提交

发布稿应包含：目标项目与类型、标题、全部正文与专用字段、验收标准、原型或证据清单、版本与人员安排、实际使用的默认值，以及门禁结论。不要只展示摘要让用户批准看不见的正文。

- 用户已提供完整且通过门禁的内容并明确要求发布，或此前已确认同一份未变化的完整草稿，视为已有授权，继续执行，不重复确认。
- 若 Agent 新补充了实质规则、范围、验收条件或替换了附件，先把完整结果做成可审阅草稿，再请求用户确认这些变更并发布。说明确认针对哪些尚未由用户决定的内容；不要把泛泛的“帮我写一个”当作对后续推测的确认。
- 只有排版、纠正错字、将已确认原型转成附件 ID 等不改变含义的操作，不重新索要确认。
- 按 [MCP 发布说明](references/mcp-publishing.md) 上传、绑定、提交和回读。不得为绕过失败而删掉必要附件、改掉目标项目或移除用户要求的负责人。

### 6. 返回可交接的结果

- **未发布：**完整草稿、阻塞项及最少补充问题。明确哪些是提报事实、哪些是待确认建议。
- **已创建或已更新：**事项链接、项目与类型、原型或证据绑定结果、版本及指派情况；说明发布或指派不会自动启动开发。
- **结果不明：**保留原 requestId，查询原请求；不要宣称成功或用新 ID 再建一条。

## 对话入口示例

用户可以直接说：

- “用 $web-coding-issue-authoring 把这份页面原型整理成需求，项目是……，我确认后发布。”
- “运营反馈活动名额计算不对，用 $web-coding-issue-authoring 整理 Bug；以下是发生时间、操作过程和截图。”
- “用 $web-coding-issue-authoring 提交一个接口幂等需求，以下是规则和验收用例，没有页面改动。”

不恭维，不用空泛的“建议进一步完善”代替明确缺口；让下一位接手者能直接从事项理解要做什么、何时允许开始、怎样判定完成。
