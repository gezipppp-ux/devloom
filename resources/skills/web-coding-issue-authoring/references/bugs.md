# Bug 规范与模板

Bug 描述可观察事实与偏离约定的行为，不要求提报人证明代码根因。产品、运营和研发提供的信息采用同一质量门禁。

## 四项必填如何判断合格

| MCP 字段 | 必须表达的内容 | 不合格示例 |
| --- | --- | --- |
| `description` | 哪个页面、接口或流程出现什么问题，相关环境与影响范围；版本未知时如实说明 | “功能不好用”“见截图” |
| `reproductionSteps` | 前置条件、必要数据、入口及编号操作步骤；读者能执行或据此调查偶发故障 | “点击一下就报错”“偶现，自己试试” |
| `expectedResult` | 对应步骤之后应出现的确定结果，及既有需求、规则、原型或已确认行为依据 | “应该正常”“应该更方便” |
| `actualResult` | 对应步骤实际出现的显示、响应、数据或状态；如有报错保留可用原文 | “不对”“和预期不符” |

描述里有这些信息仍不够，提交时必须拆到四个专用字段。截图、录屏或日志不能替代文字描述。

## 环境、复现与影响

- 收集影响复现的环境：线上或测试环境、版本或构建号、页面或接口、账号角色与权限、必要业务数据。仅在相关时收集浏览器、操作系统、设备、网络状态。
- 版本等细节暂时未知但不妨碍定位，可以标记“未获取”；关键触发条件或预期行为不明则阻止发布。不要机械要求每条 Bug 都提供相同环境字段。
- 用可安全重建的示例描述数据，不写账号密码、Token 或无必要的个人信息。日志与截图先检查需要遮盖的敏感信息；遮盖后不改变缺陷证据的含义。
- 写明观察时间与时区（时间相关故障）、出现频率或已知次数、受影响操作、是否存在绕行办法。未知写未知，不把“用户遇到过”扩写成“必现”。
- 对偶发问题，复现步骤写最近一次真实事件的操作链、前置条件、时间窗口和现有证据，注明“尚未稳定复现”。已有明确预期、实际偏差和可调查的事件线索时可以提报；只剩一句“偶尔不行”则需要补充。
- 用户提供的步骤可以直接整理为提报资料，标注“提报人描述，Agent 未执行复现”；只有实际做过安全验证才说“已复现”。不在生产环境重复扣款、发送消息、清除数据或执行真实开发任务来验证。
- 根因推测放在可选“排查线索”里并标明未经验证；不把“可能是缓存”当作复现结果或强制实现方案。

## 截图与其他证据

截图可选，没有截图本身不构成阻塞。有截图时按 [原型与附件检查](prototypes.md) 实际读取，标明对应步骤、现象区域和环境；与故障无关或含义不清的图先核实，不乱贴。用户提供的有效证据上传失败时停止发布，不悄悄省略。

普通 Bug 无需为了恢复已约定行为额外制作新原型。修复诉求包含新的页面布局或交互决策时，识别这部分属于需求，适用页面原型门禁；不要借 Bug 类型绕开页面需求规则。

## 可直接填充的 Bug 稿

```markdown
标题：[页面或功能] 在[触发条件]后出现[可观察异常]

description:
## 问题描述
- 问题与发生位置：
- 环境与相关版本：
- 角色与必要数据：
- 影响范围与绕行办法：
- 频率 / 发生时间（相关时）：
- 资料来源与复现状态：

reproductionSteps:
前置条件：
1. 从明确入口进入。
2. 输入具体数据或执行具体操作。
3. 在明确位置观察结果。

expectedResult:
- 对应步骤应该出现的结果：
- 判断依据：

actualResult:
- 对应步骤实际出现的结果：
- 错误文案、响应或数据变化：
- 相关截图 / 录屏 / 日志（有则引用，无则省略）：

acceptanceCriteria（字符串数组）:
- "按原复现步骤操作后，原偏差消失并达到预期结果。"
- "与本缺陷相关的边界或相邻路径及明确结果。"
```

将提示填成事实后才提交。`acceptanceCriteria` 以字符串数组逐条提交具体修复验证用例；四项必填中的任一项不能用“见验收”替代。

`priority` 表示处理顺序，`severity` 表示实际影响，二者分别判断；没有团队定义或影响依据时使用系统默认 `normal` 并在发布稿说明，不因提报人职位、语气或“线上”二字自动升为最高级。用户指定值时保留；值的含义与影响描述明显矛盾时先指出具体矛盾。

## 完整内容示例：不依赖截图也能复现

以下为教学用假设事实，不得当作本次真实环境或自动发布。

**title：**需求列表清空日期后仍保留原日期筛选结果

**description：**测试环境 v1.2.3，Windows 11 / Edge；有项目事项查看权限的成员在需求列表操作。清空截止日期筛选后，日期范围外的需求仍未出现；刷新页面可恢复。提报人在同一测试数据下尝试 3 次均出现，Agent 未执行复现。该问题使用户误认为部分需求不存在；未观察到数据丢失。

**reproductionSteps：**

前置条件：同一项目中存在 A（截止日期 2026-11-10）、B（2026-12-10）和 C（未设置截止日期），三条记录均可见。清空关键词、状态等其他筛选。

1. 打开该项目需求列表，确认 A、B、C 均可见。
2. 将截止日期范围设为 2026-11-01 至 2026-11-30 并应用，确认只显示 A。
3. 点击“清空日期”，观察日期控件与列表。

**expectedResult：**根据本例假定的已确认筛选规则，清空日期应移除日期条件并重新查询，起止控件均为空，A、B、C 全部可见。

**actualResult：**起止控件已经清空，列表仍仅显示 A，B、C 未出现；手动刷新页面后 A、B、C 均出现。无截图。

**acceptanceCriteria：**

- AC1：按步骤 1–3 操作，清空后显示 A、B、C，无需手动刷新。
- AC2：再次应用同一日期范围只显示 A，再次清空仍显示 A、B、C。
- AC3：另设仅匹配 B 的关键词后清空日期，仍只显示 B，关键词不会被清空。

真实提报时需替换为真实环境和预期依据；“本例假定”不是可发布的业务证据。
