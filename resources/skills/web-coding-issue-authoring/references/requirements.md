# 需求规范与模板

本文件用于新增能力、行为调整、运营规则、技术改造和非缺陷类优化。不要以“技术需求”或“运营需求”为由免除边界与验收要求。

## 发布前必须确定的内容

| 项目 | 写到什么程度才可实施 |
| --- | --- |
| 问题与目标 | 谁在什么场景遇到什么问题，本次改变哪一种可观察结果；未承诺业务指标时不要编造转化率目标 |
| 范围 | 本次包含的页面、入口、角色或接口，以及容易误解为包含但实际不做的部分 |
| 主流程 | 前置条件 → 触发动作 → 判断规则 → 系统输出 → 后续状态 |
| 规则 | 每条赋予 R 编号，写清输入、条件、动作、输出；遇到冲突说明优先级 |
| 边界与异常 | 按实际涉及的空值、上下限、重复操作、失败重试、权限、跨日或时区给出确定行为 |
| 页面变化 | 目标原型附件及入口，原型版本、涉及区域、交互和关键状态；图文不能冲突 |
| 非页面变化 | 接口或事件的输入输出示例、错误行为、数据影响；兼容性或迁移确实涉及才填写 |
| 实施依赖 | 外部接口、规则批准、测试数据等具体依赖及当前可用证据；阻塞依赖未落实时不发布为可实施需求 |
| 验收 | AC 编号、对应 R 编号、前置条件、输入或动作、可观察结果和验证方式 |

业务负责人默认当前提报账号时应在发布稿中说明。不要因为未排期、未指定开发人或未选择版本而一律阻塞；只有用户要求或本次流程确实要求时才必须补齐。也不能把“暂未排期”误写成“没有实施条件”。

不要求产品或运营替研发决定内部类名、数据库索引或框架。技术实现建议单独标为建议；用户已明确的兼容、安全或性能限制则是正式约束。

## 消除模糊边界

下列说法只有转成可观察约定后才能进入正式规则：

| 原说法 | 需要确定的内容 |
| --- | --- |
| “支持按日期筛选” | 哪个日期字段、日历日期还是时间戳、起止边界、单边范围、空日期、非法范围、与其他筛选的组合方式 |
| “优化加载速度” | 操作与数据规模、测量环境、计时起止、采样方式和目标；不能由 Agent 随意定一个毫秒数 |
| “适配手机” | 要支持的视口或设备范围、布局变化、必须能完成的操作与溢出规则 |
| “活动结束后不能参与” | 活动时间、时区、结束瞬间是否包含、已开始流程如何处理、失败提示 |
| “防止重复提交” | 重复判定维度、时间范围、首次处理中和已完成时的返回值、副作用是否重复 |
| “按原来逻辑” | 可以访问的基准文档、事项或已核验行为及精确范围，不能只写一句“保持原样” |

“正常、合理、适当、尽快、兼容所有、体验更好、等、相关逻辑”不得作为唯一的边界或通过条件。无法从证据确定的核心决策列为阻塞；可以给选项，不能冒充用户已决定。

## 可直接填充的需求稿

以下是结构模板。将提示替换为真实信息；不适用部分写明原因或删除，正式发布前不得留有未完成占位符。

```markdown
标题：[对象或页面] 在[触发条件]下支持[可观察能力]

description:
## 背景与目标
- 使用者和场景：
- 当前问题及依据：
- 本次目标：

## 范围
- 本次包含：
- 本次不包含的易混淆内容：
- 入口与适用角色：

## 前置条件与流程
- 前置条件：
- 主流程：
- 分支或失败后如何继续：

## 业务规则
| 编号 | 条件与输入 | 动作与输出 | 边界或异常 |
| --- | --- | --- | --- |
| R1 | | | |

## 原型与交互 / 接口与数据
- 是否涉及页面变化：
- 原型附件、版本、入口和覆盖状态；或不适用理由：
- 非页面需求的输入输出、错误示例和数据影响：

## 实施门禁与依赖
- 开始实施前必须满足的条件及当前证据：
- 外部依赖和联系职责（仅存在依赖时）：

acceptanceCriteria:
| 编号 | 规则 | 前置条件 | 输入与操作 | 预期结果 | 验证方法 |
| --- | --- | --- | --- | --- | --- |
| AC1 | R1 | | | | |
```

`description` 与 `acceptanceCriteria` 必须分别传给 MCP，不把验收标准只藏在正文或附件里。发布前把人员、版本、优先级、截止日期与标签另行映射到结构化字段，不把这些值写进正文就当作已设置。

## 验收如何形成闭环

- 每条核心规则至少能找到一个验收用例；用例不得引入正文没有的新业务规则。
- 用例写清“在什么条件下，执行什么动作，检查什么结果”。数据变化写明前后状态，接口写明响应与副作用，页面写明显示与可操作结果。
- 正常路径之外，只覆盖本次变化相关的失败、边界、权限和重复操作。没有金额就不强加金额测试，没有页面就不强加屏幕适配。
- 视觉验收引用已确认原型的版本与区域；交互行为仍要文字描述。不得仅写“与原型一致”“测试通过”“无 Bug”。
- 性能、稳定性或业务成效若是目标，必须确定可测条件；普通需求不要机械加上“2 秒”“99.9%”等无来源承诺。
- 区分**实施前条件**与**完成后条件**：原型可读、业务决策明确、依赖可用是前者；AC 通过并记录证据是后者。测试尚未执行不阻止创建，但验收方法不明确会阻止创建。

## 示例：把日期筛选写成可验证规则

以下是教学示例，不是当前项目已确认需求。示例没有附带实际原型，不能原样发布或宣称通过页面门禁。

范围：在项目需求列表新增“截止日期”起止日期筛选，作用于 `dueDate`；不修改 Bug 列表，不增加通知。适用于有权查看该项目需求列表的成员，不改变既有数据访问权限。

| 编号 | 已确定规则（示例） |
| --- | --- |
| R1 | 起止均有值时采用闭区间；只有起日时取大于等于起日，只有止日时取小于等于止日。按日历日期比较，不转换时间戳。 |
| R2 | 任一日期边界存在时排除 `dueDate` 为空的需求；两个边界均为空时不按日期排除。 |
| R3 | 日期条件与关键词、状态条件取交集；点击“应用”后提交，成功后回到第一页；其他筛选保留。 |
| R4 | 起日晚于止日时，显示“开始日期不能晚于结束日期”，不提交查询，保留上次成功的列表。 |
| R5 | 点击“清空日期”移除两个日期条件并查询，回到第一页；关键词和状态保留。 |
| R6 | 查询期间禁用“应用”和“清空日期”以避免重复请求；成功无结果时展示空状态，失败时保留上次结果并显示错误与重试入口。 |

验收数据：在已限定的项目、关键词和状态条件内，准备 A=2026-11-01、B=2026-11-10、C=2026-11-20、D=未设截止日期，以及不满足关键词的 E=2026-11-10。

| 编号 | 规则 | 操作 | 预期结果 |
| --- | --- | --- | --- |
| AC1 | R1、R2、R3 | 应用 11-01 至 11-10 | 返回 A、B；C、D、E 不出现，位于第一页 |
| AC2 | R1、R2 | 分别只填起日 11-10、只填止日 11-10 | 前者返回 B、C，后者返回 A、B；两次均排除 D、E |
| AC3 | R4 | 在已有成功结果后应用 11-20 至 11-01 | 出现指定提示，没有新查询，列表保留 |
| AC4 | R2、R5 | 在第二页点击“清空日期” | 返回 A、B、C、D 所属结果集的第一页；E 仍被关键词排除 |
| AC5 | R6 | 分别模拟慢响应、空结果、失败后重试成功 | 请求期间按钮禁用；空结果展示空状态；失败保留结果并可重试，成功恢复操作 |

还需取得与这些规则一致的实际原型，核对加载、空结果、日期错误与失败提示位置，才能通过 G3。验证方法可使用界面操作与请求观察；不要为写这条需求在生产环境制造故障。
