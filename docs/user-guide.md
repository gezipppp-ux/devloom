## 项目与开发空间

管理员的「全部项目」展示所有项目，管理员可管理成员、配置、需求／Bug、评论、交付和普通资产；无需先加入项目或分配部门。代码、Agent 会话、敏感资产字段仍需成员及部门授权，个人开发空间只属于本人。普通成员的「我的项目」显示获准访问的项目。

有创建资格时，点击「创建项目」，填写名称、说明和 Git 仓库地址即可引入仓库，无需预先登记。项目不归属部门，可以邀请不同部门的成员；成员所属部门仍限定其可用功能上限。一个项目保存一个仓库地址；创建时不需要个人 Git 凭据，也不会立即克隆或启动开发。创建者成为负责人，在项目「成员」中分配工作内容及权限。

项目成员获得代码操作权限后，系统自动分配个人开发空间。成员在项目「代码与环境」选择自己的 Git 账号，点击「验证访问并准备空间」进行检查和后台克隆。页面关闭不取消已经受理的准备；成功后打开开发工作台。失败后检查原因并明确重试，服务重启不会自动重复操作，失败目录保留。没有开发权限的成员直接使用需求、Bug 和资产，无需配置 Git 或使用 Agent。


项目和执行空间通过页面地址定位，支持刷新、浏览器前进和后退。项目名称在项目设置中维护，不改变已记录的代码目录。开发空间只开放给对应成员，切换页面不停止已启动的后台任务。

当前数据库结构**不迁移或读取旧的工作区配置、runs 和 uploads**。旧资料和业务 Worktree 保留原位，不会自动清理或重新执行旧任务。

## 版本、事项流程与开发任务

项目「版本」维护发布计划，例如 `v0.2`。需求／Bug 可以关联目标版本，也可以暂不排期；列表支持版本筛选。版本中所有事项已完成或取消、相关开发任务全部结束后，才能整体归档。归档内容只读，勾选包含归档后可查看；恢复版本后可继续编辑。

管理员在「系统设置 → 流程编排」统一维护需求和 Bug 的状态图，所有项目共用。选择节点修改名称、类型和是否允许开发；拖动或用方向键调整位置，在连线中选择来源、目标、操作权限和是否必须填写原因。先保存草稿，再校验发布。发布只影响各项目的新建事项，已有事项继续使用原流程版本。项目成员可查看事项绑定的流程，并按授权流转事项；项目中不提供流程配置。

需求默认流程为规划中 → 开发中 → 待验证 → 验证中 → 已实现，另有拒绝、退回和重新打开。Bug 默认流程为待处理 → 处理中 → 已解决待验证 → 已验证待关闭 → 已关闭，另有失败待处理与取消。人工业务流转与 Agent 执行结果独立；任务运行完成不会自动表示验收通过。

选择一条或多条事项，点击「认领」分配给自己，或点击「指派」选择开发负责人。每条事项分别进入负责人的待开发任务，此时无需 Git。同一事项只能存在一个未结束任务；任务启动前可修改标题、重新指派，取消后释放认领。

在「开发任务 → 我的开发任务」中，可以多选同项目、同版本、尚未启动的本人任务，点击「合并所选任务」并填写标题。合并后所有事项由一个 Codex 会话处理，来源任务和事项历史仍可追溯；需求和缺陷继续按各自的业务流程验证。

执行人在「开发任务」详情准备自己的 Git 和开发空间，从实时远端分支列表选择本次基线，再点击「确认并开始开发」。启动保存事项内容快照，并获取远端最新提交后创建 worktree。完成或取消任务要求会话空闲；结束后保留历史，原会话不能再执行。协作成员可查看计划，个人会话仍仅对拥有者开放。

## 账号与三层设置

使用唯一用户名登录，界面主要展示显示名称。管理员在「账号管理」创建或编辑显示名称，用户也可以在「个人设置 → 个人资料」修改自己的显示名称。名称可重复，选人和账号管理同时显示用户名帮助区分；改名不更改登录名，不退出当前登录，也不修改开发目录。

- 「个人设置」由成员本人维护：Git 账号、通知开关、默认任务分组、默认模型、思考强度和执行权限，适用本人全部工作区。
- 「系统设置」由管理员维护：所有成员共用的成员项目与任务目录基础路径，并提供环境检测和工具安装／更新。缺失的 Codex CLI 可通过 npm 自动安装；Git 支持 Windows winget 和 Linux APT/DNF，Linux 系统安装要求服务账号已有 root 权限。先检查目标版本，再点击「自动安装」并确认；安装后自动检测，Codex 仍需在服务账号下完成登录，提示待重启时需重启服务后重新检测。
- 项目「设置」由获授配置权限的成员维护仓库地址和初始化命令；「提示词」维护项目默认及本人的 Bug、需求和补充模板。开发空间路径由系统生成。

成员初次使用管理员分配的密码时须改密。退出或密码重置撤销登录和实时连接；已启动任务继续运行。管理员可在「账号管理」重置成员密码。浏览器通知授权仍由设备管理。

## 系统设置

管理员从全局导航进入「系统设置」，配置「成员目录基础路径」。这是所有开发空间共用的服务端绝对路径，默认 `~/.codex-workspaces`，可手动输入或点击「浏览服务器目录」选择服务端已有目录。Windows 支持切换磁盘；目录选择器也支持进入子目录、返回上级和输入路径。不读取浏览器所在电脑的目录，也不上传文件。手动填写的新目录会在保存时创建并检查写入权限，同时显示服务器是否已安装 Git。

准备开发空间时，服务按成员所选 Git 账号克隆项目仓库，成员根目录为 `<系统基础目录>/projects/<仓库目录名>/members/<用户名>`，仓库使用 `repository-<准备修订号>` 子目录，任务使用 `worktree/<任务>`。仓库目录名从 Git 地址末尾取名并去掉 `.git`（如 `web-coding`），成员目录使用登录用户名（如 `admin`）。后创建的同名仓库项目自动加 8 位短后缀，忽略大小写判重，分配结果持久化。修改项目显示名称、用户显示名称或系统基础目录不会移动已记录路径。Windows 保留用户名使用安全编码。本版不兼容旧 UUID 目录与历史项目数据，不提供搬移或迁移。

## Git 账号与连接检测

在「个人设置 → Git 账号」填写 Git 服务主机及个人认证信息，具体仓库地址在项目中维护。一个主机账号可用于本人参与的多个项目。HTTP 和 HTTPS 支持用户名与密码或个人访问令牌；SSH 使用生成的密钥。提交作者姓名与邮箱单独配置。

SSH 账号点击「生成 SSH 密钥」，将展示的公钥复制到 Git 服务的 SSH 密钥设置。私钥由服务器加密保存，不回显、不接受手工填写；服务器需安装 OpenSSH（`ssh-keygen`）。未保存的密钥草稿有效期为 24 小时，再次生成会替换旧草稿，不影响已保存密钥。

Gitee SSH 账号的 Git 主机填写 `gitee.com`，不带 `git@` 或仓库路径。项目可填写 `https://gitee.com/空间名/仓库名.git` 或 `git@gitee.com:空间名/仓库名.git`，检测和准备空间时会按所选账号使用等价 HTTPS／SSH 地址。HTTP 账号主机填写 `https://gitee.com`。其他 Git 服务及自定义端口需保持账号与项目仓库地址的主机和认证方式一致。

填写账号后可点击「验证登录」，直接验证 Git 主机，无需选择项目，也不会保存当前草稿。SSH 请先添加公钥；HTTP/HTTPS 主机验证使用可读取本人资料的个人访问令牌，用户名需与令牌所属登录账号一致，此验证接口不支持普通密码。Gitee、GitHub、GitLab 官方主机自动识别，自建 GitLab 或 GitHub Enterprise 请在「登录验证服务」选择对应类型；其他服务可通过准备开发空间检测仓库访问。验证失败会保留已填写内容，编辑时密码留空会使用已保存凭据。

保存账号与验证登录是独立操作。主机验证成功后仍需点击「保存 Git 账号」；项目开发空间准备时检测实际仓库读取权限，不代表推送权限。被开发空间使用的账号不能删除或改变主机／认证方式，但可以更新同类型凭据。克隆、后续 fetch 及工作区内 Agent 发起的 Git 网络操作均使用所选账号，凭据不写入仓库地址或配置。

更新 Git 凭据不会中断正在执行的轮次或审批。工作区全部轮次、启动及命令操作空闲后，下次启动任务或续聊会自动重连并读取新凭据，保留原 session 和 Worktree；异常断线重连也重新读取，无需重启服务。Codex 使用隔离认证配置，同时从服务用户的系统／全局 Git 配置中保留提交身份默认值（`user.name/email/useConfigOnly`、`author.name/email`、`committer.name/email`），仓库自身配置仍可覆盖这些默认值；没有配置身份时不会自动伪造作者。

本次 Git／目录配置重构不兼容旧数据与旧字段，不提供自动迁移或回退。请使用新的独立数据目录部署；程序不会删除旧数据库或移动旧项目、任务目录。

## 项目设置

每个项目只有一个目标仓库，成员的开发空间使用同一项目地址、各自的凭据和代码副本。

- Git 仓库地址：创建时必填；分配开发空间前可在设置中修改，分配后只读锁定并提示原因。其他设置仍可保存。
- 仓库与 Worktree 目录：准备空间时由系统生成，不能通过项目设置改写。
- 初始化命令：每行一条，最多 20 条、每条 4000 字符、每条超时 15 分钟。Windows 使用 cmd，Linux 使用 sh。每条从新 worktree 根目录开始，互不继承 `cd` 和环境变量修改；例如 `pnpm install`、`pnpm build`。

保存只影响新任务；已有任务继续使用记录的 session、路径和分支。初始化失败、超时或停止后不启动 Codex、不修改渠道状态，保留目录和日志用于排查。不会自动重跑不确定的初始化或已有任务。

### 提示词模板

在项目「提示词」中分别维护 **Bug 提示词**、**需求提示词**和**补充提示词**，新项目已提供三份默认模板。Bug 模板侧重复现、根因修复与回归验证；需求模板侧重完整实现、验收标准与边界场景。

在待开发任务详情准备好环境并选择起始分支后，可在「启动 Codex 开发」按钮上方填写补充提示词（可选，最多 20000 字），例如实现约束和验证重点。点击启动时，补充内容会按执行人的补充模板追加到事项指令中；未填写时只发送事项指令。补充模板必须保留 `{{content}}`，可使用 `{{title}}` 引用任务标题。补充内容随启动请求一起保存，无需编辑或另存任务信息；启动前校验失败保留输入，后续补充通过会话发送。

「项目默认」由具有项目配置权限的成员维护。「我的配置」只对你在此项目执行的任务生效，不影响其他成员和其他项目。勾选“自定义此提示词，仅对我生效”后编辑；未自定义的类型持续跟随项目默认。点击“恢复跟随项目”或“恢复内置默认”后，仍需保存才会生效。

模板支持点击插入占位符、示例预览和冲突合并。Bug 和需求模板必须保留 `{{title}}`、`{{content}}`、`{{images}}`；完整资料会包含该事项的描述、验收标准或复现步骤、预期结果与实际结果。图片编号与本轮发送顺序一致。补充模板仅要求 `{{content}}`。所有模板均不能留空。

开始开发或追加事项时按事项类型使用生效模板，混合任务逐条渲染；已保存的任务和追加资料快照保持不变。本次移除“手动任务提示词”旧字段，旧提示词数据不兼容、不自动转换。

使用 `{{名称}}` 占位符自动填入本次需求，须保留 `{{title}}`（标题）、`{{content}}`（需求正文）、`{{images}}`（图片说明与有序列表）；可选 `{{image_count}}`、`{{image_list}}`。例如：

```text
请根据以下需求完成开发，遵循仓库 AGENTS.md，运行检查并报告结果。
未经用户要求不要提交、推送或发布。
标题：{{title}}
--- 需求资料开始 ---
{{content}}
--- 需求资料结束 ---
{{images}}
```

每个模板最多 20000 字符；空模板、未知或未闭合的占位符、缺少必填占位符会阻止保存。替换仅进行一次，需求正文中的占位符文本不会再次展开，不支持表达式或脚本。图片仍作为附件按顺序传入，预览使用示例数据。

项目默认与个人覆盖分别保存在 PostgreSQL 的项目设置和成员配置中；保存时保留仓库及开发空间。显式文件配置的 `prompt_templates` 同样只接受 `bug`、`requirement` 两种模板。

项目和需求／Bug 不设置开发基线。待开发任务启动前必须从实时远端列表选择本次分支，不支持手动输入或使用过期列表回退。任务详情记录分支、实际提交和获取时间。获取失败保留原因且不启动 Agent；已有会话继续原基线，不会自动重新拉取或切换分支。

## 每个需求的模型、思考强度与权限

在「从需求启动」中为本次需求选择 Codex 模型和思考强度。每次新建需求使用当前成员的个人默认值；未设置模型或强度时沿用 Codex 默认配置。每个任务可独立选择，模型列表实时读取服务端 Codex，加载失败可刷新重试并保留当前选择。

选择具体模型后，思考强度下拉框只显示该模型支持的选项，也可使用默认强度。切换模型会清除不支持的强度。工作区不再设置模型或思考强度，旧工作区中的这两项不影响新任务。

创建需求时同时选择权限，初始值来自个人设置；未修改个人设置时为「请求批准」：

- 请求批准：使用工作区写入沙箱，写入工作区外文件或访问网络时按需请求用户批准。
- 帮我批准：使用同样的沙箱，由 Codex 原生自动审查权限请求，根据风险决定是否批准；当前 Codex 不支持或能力检查失败时禁用，并显示原因。
- 完全访问权限：关闭 Codex 沙箱与逐次审批，允许访问网络和本机文件。仅在信任当前任务时选择。

会话输入框左下可修改权限，右下可修改模型与思考强度，选择后立即保存。执行中修改会显示「下一轮生效」；本轮补充指令继续使用本轮设置，结束后发送的新消息使用新设置。修改不创建新会话或 worktree，也不会处理已有审批。刷新、重连与服务重启后保留选择；切回默认模型或强度时，下轮会重新读取适用的默认值。初始化中和只读任务不可修改执行设置。

## 手动图文需求

选择「手动输入」，填写标题和 Markdown 内容，可附 PNG/JPEG/WebP 图片，最多 20 张、每张 10 MiB；支持仅标题加图片。上传和运行记录都按应用工作区隔离，不能引用另一个工作区上传的图片。未使用的暂存图片 24 小时后过期，在后续上传时清理。

任务目录由「前缀＋12 位任务短标识」组成。前缀默认按标题生成，英文保留、中文转无声调拼音，最多保留 16 位。可填写「Worktree 目录前缀」，只支持 1–16 位英文字母、数字、短横线或下划线，以字母或数字开头，排除 Windows 设备名；不能传路径，系统始终追加短标识，不会覆盖已有目录。

## 类型标签与任务进度

创建任务时可选择「需求 / Bug / 其他」类型，已有任务可在右侧「信息」抽屉修改。左侧列表显示类型标签和进度，支持按类型分组、按进度分组或不分组；分组可折叠，分组方式保存到个人设置，适用本人全部工作区。

会话面包屑与标题合并为紧凑标题区，编辑图标紧随标题，执行状态标签与刷新在宽屏时对齐标题行、窄屏时放到下方，长名称自动换行。任务管理与归档、删除位于右侧「信息」抽屉。点击编辑图标可在限宽的输入区修改标题（最多 200 个字符），取消和保存紧邻输入区，窄屏时换到下方，状态和刷新保留在表单上方。Enter 保存、Escape 取消；中文输入法选词不会触发保存。标题会保存并同步到同一工作区的其他已打开页面，仅作为会话展示名称，不会修改原始需求快照、session、分支或 Worktree 路径。历史空标题显示「未命名会话 · 需求 ID」，可手动改名。

左侧列表下方的「已归档会话」可查看当前工作区的归档记录、按名称搜索、恢复或直接删除，无需先恢复。恢复后会话重新出现在需求列表，保留原有历史、会话身份和代码状态，不会自动重新执行任务；已删除的 Worktree 不会重建。删除复用会话页面的确认流程，仍有关联代码时可确认分支名后强制清理。永久删除的会话无法找回。

会话可归档或永久删除。归档后不再出现在左侧列表，但历史、需求资料和 Worktree 保留。永久删除会移除会话记录、需求资料和附件，无法恢复。有关联代码时，可先通过 Git 面板清理，或勾选「同时强制删除 Worktree、本地目录和本地分支」，输入完整本地分支名并确认后一次清理。强制删除会放弃未提交、未跟踪、忽略文件和未推送的本地提交，也会清理原任务目录中的残留文件；远程分支保留。运行中、有待处理审批、其他服务占用或目录身份不符时不能删除；清理失败保留会话和删除进度，可重试。

新任务默认为「进行中」。人工进度提供「进行中 / 待验收 / 待合并 / 已完成 / 已搁置」，在右侧「信息」抽屉选择后立即保存。Codex 的执行、停止、单轮结束和重连续聊均不自动修改人工进度，执行状态会另外显示。修改类型或进度只更新本地任务管理信息。

旧任务尚未标记时默认显示「需求、进行中」（原始类型为 Bug 的显示 Bug），可以随时手动调整；不会根据历史执行结果自动认定完成。

## Git 和会话

新任务创建的 worktree 位于：

```text
<成员目录基础路径>/<用户名>/worktree/<项目名>/<任务前缀>-<12 位任务短标识>
```

例如 `D:\wt\alice\worktree\project-a\login-a1b2c3d4e5f6`。任务目录最多 29 位，不再叠加仓库哈希目录或重复的工作区 UUID。分支为 `codex/<12 位任务短标识>`，短标识由仓库真实路径、完整工作区 ID 和需求来源身份共同生成，不受标题或自定义前缀变化影响。同名任务仍保持隔离；目录或分支已存在时拒绝创建。

用户名目录仅用于新任务。已有任务继续使用记录的 session、分支和 Worktree 路径，包括旧的 `u-<成员 UUID>` 目录，不重命名、不搬移。

Windows 创建前会检查目标提交中的文件和目录路径长度，过长时显示具体路径并提示缩短系统基础目录或工作区目录，在创建分支及检出文件前停止。建议基础目录使用 `D:\wt` 等短路径，为仓库内部目录留出空间。该检查覆盖 Git 已跟踪内容，依赖安装和构建生成的文件仍受系统路径限制。

根仓库不会切换分支、stash、提交或带入未提交的更改；不会复制 `.env`、Cookie 或 node_modules。任务结束保留 worktree。服务不会自动合并、推送、删除分支或验收需求。

点击左侧工作区名称下的「代码仓库」可管理 Git 更新。「获取远端更新」使用已配置的远端刷新远程跟踪分支，不改变已有任务代码。「更新基准分支」会先获取其上游，再仅以快进方式更新；要求基准是仓库当前检出的本地分支、已配置远端上游且目录干净。若分支分叉、存在本地修改或 Git 操作未结束，会提示原因，交由 Codex 或本地工具处理。新任务会自动获取所选 origin 分支的最新提交，再创建独立工作树，无需先手动更新本地检出分支。网络操作使用工作区关联的个人 Git 账号，不弹出登录窗口。

右侧「Git」入口打开 Worktree 抽屉，显示未提交文件、待推送提交和落后远端数量；可查看当前实际检出的分支、路径及上游。未提交文件包含已跟踪修改与未跟踪文件，忽略条目另列。提交数量与当前分支的远端上游比较；没有上游显示「分支尚未发布」，读取失败显示未知，不当作 0。状态在打开会话、任务状态变化或手动刷新时读取；远端比较基于最近获取的本地记录。任务记录的初始分支不因目录内切换分支而阻止继续会话，但删除 Worktree 仍要求回到记录分支并完成该分支的确认。合并和冲突处理由会话中的 Codex 完成，界面不提供合并或冲突处理按钮。

Git 面板提供「删除 Worktree 与本地分支」：展示任务目录、完整分支名及风险，需要输入分支名确认；有未提交、未推送、尚未发布或忽略内容时，还须确认丢弃本地内容。运行中、其他服务占用、Git 操作进行中、目录身份不符或确认后状态变化都会阻止删除。只通过 Git 删除登记的任务 Worktree 和对应本地分支，不删除远程分支。目录删除成功而分支删除失败时保留进度，刷新后可重试分支清理。删除后会话历史、需求资料和记录保留，任务转为只读；人工进度保持原值。

Web 使用 `codex app-server --stdio`，按任务选择设置审批与沙箱。需由用户处理的命令和文件审批、澄清问题在页面显式显示。输入框可发送后续指令，执行中可补充指令或停止当前轮；始终沿用原 session。关闭浏览器不停止任务；正常关闭服务会请求中断活动任务，重启后可继续。

支持 GPT-6 等模型通过 Codex `request_user_input` 发起的提问。需要等待回答的问题会自动弹出，展示多个问题、选项说明，并允许输入自己的回答；必须点击「提交回答」才会发送。可按 Escape 或「稍后回答」收起，再从会话中的「回答问题」打开。非阻塞问题不会暂停补充指令；刷新页面可恢复仍有效的问题，已失效或轮次结束的问题自动移除。此能力按 Codex 协议接入，不限定模型名称。

会话输入框支持直接粘贴剪贴板中的截图或图片（Ctrl + V），也可点击权限左侧的「＋」选择文件。发送前可预览、移除，支持图文一起发送或仅发送图片；执行中也可补充图片。每条消息最多 20 张 PNG/JPEG/WebP，每张不超过 10 MiB。上传完成后可点击发送或按 Enter，Shift + Enter 换行；中文输入法选词确认时不会发送。上传失败可重试，发送失败保留草稿。已发送图片随会话历史展示，并按工作区和任务隔离保存。

Codex 回复按 Markdown 显示，支持标题、列表、加粗、行内代码、代码块、引用、表格和链接；流式回复与历史记录使用相同格式。长代码和表格可在内容区横向滚动。回复中的 HTML 源码按文字显示，Markdown 图片仅显示替代文字；用户消息和工具输出保留原文。

回复中的本地文件链接和行内代码文件名可点击，在对话右侧打开只读文件面板。支持源码高亮、行号定位、复制、刷新，以及统一差异和左右对照；桌面可加宽面板，窄屏覆盖显示，手机使用统一差异。默认「任务累计变更」比较任务创建时记录的提交与当前文件（含已提交和未提交内容），也可选择「未提交变更」与当前 HEAD 比较。Git 抽屉的变更文件列表使用同一查看器。只有文件名且有多个匹配时选择完整路径；已删除文件可在差异中查看删除前内容，重命名显示原路径。

文件只从当前会话记录的 Worktree 读取，不读取主仓库或其他任务目录；忽略文件、Git 元数据、目录链接和符号链接不开放预览。历史消息打开的是当前文件，面板标明读取时间，不表示那轮对话结束时的快照。Worktree 已删除时无法再预览；缺失起始提交时明确提示，可切换未提交变更，不自动改用其他基准。源码保留原始文本，行差异统一 CRLF/LF 换行；二进制、非 UTF-8、超过 512 KiB 或 10000 行的文件显示限制说明。

会话详情采用宽屏工作台布局：桌面左栏共 304px，消息区与输入框同宽、上限 1440px；用户消息和 Codex 回复正文为 14px，思考摘要等工具标题为 13px，命令文字为 12px。桌面输入文字为 14px，手机编辑框保留 16px 以避免输入时自动放大。输入框默认两行，可拖动增高，图片和错误反馈自然展开；下方提示合并排列。右侧「信息 / Git / 需求」入口按需打开抽屉，默认收起；再次点击当前入口、点击收起、抽屉外区域或按 Escape 可关闭。抽屉独立滚动，不挤压对话区；切换资料保留消息草稿和对话位置。历史消息、命令输出和文件修改在对话区展示，启动时的完整需求快照、图片和实际提示词在「需求」抽屉查看。已移除或未注册的 worktree 只读。记录中的路径是权威值，修改安装路径或设置不会搬动业务 worktree。



## 认领、指派与合并开发

1. 新建或导入需求／缺陷，维护描述、验收标准或复现步骤。
2. 在事项列表勾选后点击「认领」分配给自己，或点击「指派」选择开发负责人。每条事项分别进入该成员的待开发任务，此时无需配置 Git。
3. 打开项目的「开发任务 → 我的开发任务」。可以直接开发一条任务，也可以勾选多个同版本任务，点击「合并所选任务」，填写清晰的合并标题。需求和缺陷可以一起选择，但已开始执行或他人的任务不能合并。
4. 在任务详情准备开发环境、选择远端开发分支，再点击「确认并开始开发」。Codex 会同时获得所有关联事项的资料，并在一个会话中开发。
5. 开发结束后人工确认任务完成，再按需求／缺陷各自的业务流程验证。合并来源可追溯，Codex 的执行结果不会自动替代业务验收。

「项目全部任务」用于协作查看；未启动任务可以重新指派，取消任务会释放认领。当前版本不兼容旧开发任务请求和历史快照格式。
