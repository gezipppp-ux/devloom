# 无需启动 Agent 的成果送验方案

日期：2026-10-16。状态：原成果送验功能已交付；本轮按用户选定的 A 方案调整 UI 与流程配置读取，正在隔离验收。

推荐结论：流程编排是业务路径的唯一依据；交付能力与 Agent 执行解耦。发布显式的新流程版本，以受控的应用操作让符合条件的既有事项采用新版本，不通过代码给旧流程增加隐含路径。

## 目标与边界

事项通过已有成果、配置调整或人工处理完成后，可以直接提交成果并进入验证，无需为了流转启动 Codex。验证通过仍是需求完成的前提。

本次实施范围为仓库代码、工程契约与隔离验证。不直接修改生产数据库，不变更表结构，不执行数据库迁移、回填或修数，也不部署或代替用户操作两条真实事项。功能上线后，发布流程、切换事项所用版本和提交交付均是应用内的正常业务操作，会保存对应业务数据及审计。

## 已核实的现状

通过当前 Web Coding MCP 连接只读查询「MY智营」项目及事项详情；未直连用户提供的数据库。两条事项属于 v1.4.0，均绑定系统需求流程 v1。

| 事项 | 当前状态 | 当前分派 | 业务目标 |
| --- | --- | --- | --- |
| #5 视频结果页支持当前页面直接下载视频 | 待开发 | 已有待开发任务，执行人为测试#研发 | 用户说明已经开发完成；提交已有成果并送验 |
| #10 图生图保留图片文字设计并移除额外营销文案 | 规划中 | 当前处理人为刘嘉辉，尚无开发任务 | 用户确认通过配置或人工处理完成，仍需验收 |

两条事项均未配置 QA 或业务验收人，因此送验时必须明确选择有效验证人。

当前有三层限制：

1. 默认流程只有真实 `development.started` 才能从待开发进入开发中，且只有开发中、待返工提供 `delivery.submitted`。
2. 关联开发任务的交付要求任务已经启动并有 run key；即使只开放按钮，未启动任务仍无法提交。
3. 任务收尾仅处理已经启动的任务；无开发任务的人工成果退回时，默认返工交接又依赖开发负责人。

## 建议的业务规则

### R1：提交已有开发成果

待开发的当前任务执行人在事项详情或开发任务详情选择配置的送验操作（推荐模板命名「线下处理」），填写成果说明、核验结果并选择验证人。

- 允许关联本人尚未启动、没有运行记录的待开发任务；保留原任务、执行人和事项关联。
- 直接从待开发进入待验证。提交标识或代码提交信息可选，不以当前系统必须存在 Agent 会话作为交付条件。
- 不记录虚构的执行开始时间，不生成会话、运行记录、工作树或 `development.started` 事件。
- 存在准备中、启动中、运行中、结果未知或待恢复的真实执行时，继续执行原有阻断与核对规则。
- 已经运行并完成本轮执行的任务沿用正常送验规则。

### R2：线下处理统一沿用已有成果流程

配置或人工处理完成后，沿用已有成果的交付表单、指定验证人、验证及返工流程，不增加线下状态或独立业务流。推荐模板在待开发及后续适用阶段配置送验入口，不在规划节点配置直接送验。

- 入口、名称和目标以事项绑定的已发布流程为准，代码不按节点名称、ID、类别或顺序写死可用阶段。
- 管理员可在流程图中调整 `delivery.submitted` 连线的来源、名称、目标、操作主体和交接规则；发布后用于新事项，旧事项继续使用绑定版本，满足条件时显式采用新版本。
- 自定义流程若允许无任务的当前处理人送验，保留原权限、来源和验证门禁；无需创建虚构的 Agent 运行记录。

### R3：保留验证与返工闭环

同一入口复用交付说明、验收清单、指定验证人、开始验证、验证通过及退回原因等能力。

- 明确选择具有交付验证和事项验证权限的有效成员，不默认作者，也不强制新增 QA 职责。
- 验证通过后需求进入已实现。
- 已有成果退回后仍交给原开发执行人，在原任务上处理并沿原交付链重新提交；可以继续人工整理成果，也可以明确启动 Agent。
- 两类成果退回后均进入流程明确配置的待返工节点，由「本轮交付提交人」接收。人工成果不依赖开发负责人，可继续无任务重提。原提交人失效时，由业务负责人显式修复分派。
- 人工返工后若确实需要开发，由用户明确安排开发；后续交付继续关联原退回链，并校验新任务的当前认领和来源变化。

### R4：工作台与任务收尾保持一致

- 提交成功后结束原处理步骤，验证人收到待验证动作；已送验范围不继续提示启动开发或重复整理成果。
- 已有成果关联的未启动任务在验证期间保留，展示等待验证；全部关联事项完成、没有待处理交付或执行后，结束任务并释放认领。
- 合并任务只推进本次选择的事项；其他事项仍可正常处理，不能因为部分事项完成就结束整个任务。
- 人工成果全过程不创建开发任务，退回后由原处理人收到待推进动作。

## 页面方案

在现有事项详情与成果表单中增加入口，沿用项目的中性界面和中英文文案。

| 场景 | 入口 | 表单与结果预览 |
| --- | --- | --- |
| 待开发，已有成果 | 线下处理（可配置名称） | 交付说明、核验结果、可选提交信息、验证人；预览「待开发 → 待验证」 |
| 规划中，人工完成 | 推荐模板先安排处理 | 完成前置流转后使用同一送验表单；运行时以绑定流程为准 |
| 正常开发中 | 提交交付并送验 | 沿用现有成果表单与正常流转 |
| 退回人工成果 | 修改并重新提交 | 展示退回意见，保留原交付关系与修订；预览重新进入待验证 |

提交按钮读取当前送验连线的操作名称。提交前展示当前处理人、下一验证人、事项范围和共享确认；失败保留输入，冲突刷新后由用户核对。

入口显示、按钮可用状态和流转目标以服务端返回的可操作能力为准。事项详情、任务详情、交付列表和返工入口使用同一判定，避免只放开某一个页面。

## 流程与代码各自负责什么

流程定义负责合法路径、处理主体、必填资料和验证门禁；代码负责执行这些规则、交付来源校验、事务、权限、审计和任务收尾。已有成果是否存在不由 Agent 是否启动来判定。

推荐的需求流程 v2：

| 来源 | 业务动作 | 目标 | 处理主体 / 下一处理人 |
| --- | --- | --- | --- |
| 待开发 | 线下处理，触发 `delivery.submitted` | 待验证 | 当前开发任务执行人 / 本次指定验证人 |
| 待开发 | 真实 `development.started` | 开发中 | 当前开发任务执行人 |
| 开发中 | 提交交付，触发 `delivery.submitted` | 待验证 | 当前开发任务执行人 / 本次指定验证人 |
| 待验证、验证中 | 验证通过 | 已实现 | 本轮指定验证人 |
| 待验证、验证中 | 退回并填写原因 | 待返工 | 本轮指定验证人 / 本轮交付提交人 |
| 待返工 | 沿原交付链重新提交 | 待验证 | 当前返工处理人 / 本次指定验证人 |
| 待返工 | 明确认领或安排开发 | 待开发 | 有资格的认领人或分派者 / 开发执行人 |

上述动作使用统一的交付入口，根据事项阶段和来源显示已有成果或人工成果提示。没有合法送验连线的节点不显示送验按钮。自定义流程继续执行其配置的评审、资料和验证要求。

补充一个通用交接来源「本轮交付提交人」，用于退回交接；它从当前有效交付读取，不新增事项长期职责字段。返工节点必须允许该处理人提交无代码交付，不能把配置或人工返工强制转换成开发任务。

交付来源校验改为：有关联开发任务时，校验当前任务及执行人归属；无关联任务时，校验当前处理人。允许合法的未启动任务提交已有成果；已有真实执行则保留执行结束或结果核对门禁。不得通过省略 taskId 绕过已有开发认领或运行检查。

## 既有事项如何采用新流程

发布 v2 不自动影响已绑定 v1 的事项，旧版本仍然不可变。增加受控的「采用新流程版本」能力，作为正式应用操作：

1. 操作者须有相应事项管理与流转权限。先预览原版本、目标版本、当前节点映射、下一处理人及关联开发任务影响，再明确提交。
2. 首期仅允许尚未启动、没有运行身份或待恢复事件、没有交付记录的未结束事项切换；已运行、正在验证或已有交付链的事项保留原流程，不在本需求中迁移。
3. 目标版本必须已发布且与事项类型一致，当前节点须能唯一、明确映射。沿用稳定节点 ID并核对业务属性；缺失映射、处理人资格不符或任务关系冲突时拒绝切换，不猜测状态。
4. 在同一短事务中校验事项、当前步骤和关联任务修订，保存版本引用，结束旧步骤并创建新版本的当前步骤，记录原新版本、节点、处理人、原因和请求标识。并发启动或内容变化时整笔失败。
5. 不改事项身份、开发任务身份、执行人、任务历史快照或已有运行路径。旧步骤及历史仍指向 v1；新步骤绑定 v2；旧轮次请求失效，不自动重放任何动作。
6. 两条样本在已读取的状态下符合基础条件：#5 映射待开发，保留原待开发任务；#10 映射规划中，保持无开发任务。真正切换时重新核查权限和状态，不能把方案阶段的快照作为执行依据。

这项能力只解决安全的开发前版本切换，不扩展为任意在途流程迁移系统，也不后台批量重绑。新事项直接使用新发布版本。

流程 v2 作为可加载、审阅和发布的推荐模板提供，不自动覆盖管理员草稿或已发布配置。复用现有流程 JSON、事项版本引用、交付、步骤、历史及任务字段，不新增数据库列或表，不改写已发布迁移。

## 实施范围与一致性

- `src/domain/`：推荐流程、交付主体校验、本轮提交人交接、受控版本切换的条件与映射校验。
- `src/application/`：统一交付用例及 presenter 能力；版本切换预览与提交；校验当前步骤、任务来源、验证人及权限。
- `src/storage/`：允许经过业务授权的未启动任务作为交付来源；调整任务收尾。存储层不自行决定谁能绕过业务门禁。
- `web/src/features/projects/`：接入统一送验入口、目标预览、任务等待验证状态、无任务返工重提及开发前流程版本切换。
- 系统流程编排：接入推荐模板及「本轮交付提交人」交接选项，保存草稿和发布继续使用原有显式操作。
- `docs/engineering/`：同步业务交付、真实执行及开发前流程版本切换的边界；保持流程定义为业务路径的唯一依据。

交付创建、事项状态、步骤交接及审计在同一短事务内提交。沿用稳定 requestId，并检查事项、任务及交付修订；重复请求只产生一份交付。送验与启动并发时只有一项能够通过最终校验，失败方不启动 Agent 或留下半份交付。

历史记录需明确成果来源、实际操作者、原步骤与目标步骤、交付及任务关联。流程中不制造执行事实，私人会话与代码继续只供原所有者访问。

## 验收与执行顺序

1. 在隔离环境用真实结构的 v1 定义和上述两类状态建立夹具，发布推荐 v2；确认新发布不会自动改变 v1 事项。通过受控切换保留事项及任务身份、原版本定义和历史，证明无需数据库迁移或回填。
2. 验证已有成果：不启动 Agent，从待开发提交到待验证，通过后事项完成、原待开发任务结束；退回可在原链重提。
3. 验证人工成果：无开发或会话权限的合法处理人可以提交；全程无开发任务，退回交还原处理人，重提后可通过。
4. 覆盖并发启动与送验或版本切换、重复提交、过期修订、权限撤销、无效验证人、归档、未知执行、批量部分送验、人工转开发及自定义流程不被绕过；已有交付或运行历史的事项不能误切版本。
5. 按 AGENTS.md 和 Jenkinsfile 执行 ESLint、架构/单元/集成测试、构建及全部浏览器入口；使用隔离 PostgreSQL、fake Codex 和临时 Git。检查相关界面响应式与英文状态。
6. 交付代码差异、验证结果与上线注意点。生产部署和两条真实事项的操作另行安排。

实现不包含生产配置发布、数据库操作或真实事项流转。部署后由管理员在系统流程中载入推荐模板、审阅并保存发布，再由有权限的人为符合条件的存量事项预览并采用新版本。
