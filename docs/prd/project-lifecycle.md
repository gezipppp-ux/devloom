# 版本、流程与开发任务重构 PRD

日期：2026-10-12。生命周期功能已实施；本轮按补充要求将流程归属调整为系统设置，验证见[系统流程记录](../reviews/system-workflows-2026-10-12.md)。此前生命周期验收见[记录](../reviews/project-lifecycle-2026-10-12.md)。不兼容旧接口与旧业务数据格式，不为历史行为保留双轨逻辑。

## 已确认规则

1. 项目维护发布版本，需求／Bug 关联一个目标版本，可暂不排期。版本归档前，所有事项必须处于完成或取消状态，且没有未完成开发任务；否则先处理或移出该版本。归档后内容只读，恢复版本后可再编辑。
2. 本次开发基线只能从 Git 远端实时读取的分支中选择，支持搜索和刷新，不接受手输分支。开始执行时再次获取目标分支最新提交，固定 SHA 后创建 worktree。
3. 系统设置统一维护需求和 Bug 两套流程，仅系统管理员可以编排和发布。项目不拥有独立流程、覆盖配置或流程管理权限。图形编辑支持状态节点、连线、初始／完成／取消状态、可开发节点、操作权限和必填退回原因。草稿校验后发布为不可变版本，所有项目的新事项使用系统当前版本，已创建事项继续使用所绑定版本。
4. 指派／认领先为每条事项分别创建待开发任务，不克隆、不创建 worktree、不调用 Agent。执行人在任务列表多选合并后，一个任务允许关联多个事项，一个事项同一时间只允许归属一个未结束开发任务，后端事务和数据库唯一约束同时保护。

## 交互与业务边界

默认需求模板按用户补充示例提供：规划中 → 开发中 → 待验证 → 验证中 → 已实现；另有已拒绝，以及退回开发、退回规划和重新打开的连线。默认 Bug 模板为待处理 → 处理中 → 已解决待验证 → 已验证待关闭 → 已关闭，另有失败待处理与已取消。两套都是可编辑的系统流程，不在执行器内硬编码流转；退回、拒绝及重开要求填写原因。

发布版本号独立于编辑修订号和流程定义版本。新建和编辑均强制使用小写 `v` 加两段或三段非负整数，例如 `v0.1`、`v1.0`、`v0.5.9`；各段只能为 `0` 或不以零开头的数字，最长 100 个字符，不接受空格、后缀或其他名称。前后端共用 `shared/project-release-name.json` 格式契约，后端返回 400 并阻止非法写入。已有记录不自动改名，编辑保存时须符合新规则。列表提供版本筛选，已归档版本默认隐藏，历史记录可查。

流程编排入口为「系统设置 → 流程编排」。项目仅展示事项绑定流程和允许执行的流转；状态筛选只能读取已发布版本，不向项目成员公开系统草稿。删除项目级流程页面、写接口和 `workflow.manage` 授权，不保留别名或兼容回退。系统流程发布的权限为管理员角色，事项流转的 `issue.transition`／`issue.accept` 继续按部门上限和项目授权执行。

需求／Bug 页提供“认领”和“指派”，移除直接启动开发。认领人必须是具备开发资格的有效项目成员，但此阶段无需 Git 账号或就绪空间。指派者按事项指派权限操作，不能访问被指派人的个人会话。

开发任务先保存标题、执行人、关联事项与版本，支持执行前合并同版本任务、取消／释放认领和重新指派。启动后执行人、关联范围与本次基线不能静默改写；追加资料沿用明确保存和发送动作。任务完成／取消后释放活跃认领记录，保留历史关联。执行中的任务不能取消或转派；Agent 成功返回不等于业务验收通过。

“我的开发任务”中，执行人先准备个人空间，再从远端分支列表选择基线，点击开始开发。一个规划任务对应一次明确启动，重复请求不能产生第二个 worktree；失败或结果不明不得自动重放。个人会话继续保持所有者隔离，项目成员可查看计划、负责人、业务状态与公开交付。

任务和事项业务流程不与 Agent 的运行／失败状态混用。流程里的“验证失败／退回处理”表示业务判断；网络或 Agent 失败只记录执行失败。流程节点与连线具有稳定标识；删除被连线引用的节点须先处理连线。发布校验初始节点唯一、节点可达、存在结束节点、边两端有效、权限白名单及名称有效。

## 技术与验证

以独立版本、流程定义／发布版本、开发规划任务和活跃认领实体表达职责，清理 domain 中固定状态流转及前端硬编码状态选项。HTTP 只适配服务；Git 远端查询使用当前执行人的凭据，异步等待后重验权限，不写入凭据、不依赖本地缓存冒充实时结果。

保留数据库迁移版本管理，不修改已发布迁移。新模型不读取旧字段作为兼容回退；不会为本次验证执行真实需求或向 TAPD 写入。

实施顺序：模型与规则 → 版本及流程服务 → 认领／指派及显式启动 → 远端分支选择 → 页面与流程图 → 并发、权限、归档、快照及浏览器回归 → 本地更新。

验收重点：归档门禁及只读完整覆盖；流程发布不改在途事项；产品成员可规划协作而无 Agent 操作；并发认领只有一次成功；无 Git 时仍能认领；仅执行人能启动；分支列表来自远端、获取失败不降级手输；创建／认领／指派均不触发实际开发；窄屏图编辑、弹窗与底部操作可达。

## 2026-10-12 开发流程调整

需求／缺陷与开发任务分开：在事项页认领或指派，每条事项分别创建一个待开发任务并同步开发负责人。事项编辑只维护内容和参与人，不再单独写入负责人，避免分配与任务脱节。批量分配可以跨版本，整批事务成功或整批回滚，不会提前融合或启动执行。

任务页默认显示「我的开发任务」，可切换「项目全部任务」。本人可多选同项目、同版本、未启动的任务，填写合并标题后合成一个待开发任务（最多 20 条事项，需求和缺陷可混合）。合并以各源任务修订号和请求标识校验，保留源任务及事项快照，将源任务标为「已合并」并指向新任务，原子转移活跃认领。已合并源任务不再可编辑、开始、完成或取消，也不阻碍版本归档。

合并仅整理开发范围，不修改事项业务状态，不要求 Git 环境。执行人在任务详情准备环境、选择实时远端分支，再显式开始 Codex；合并任务共享一个会话、分支及 worktree。转派同步全部关联事项的开发负责人，取消或移出事项释放认领并清空对应负责人。完成任务释放活跃认领但保留负责人及历史；Codex 返回成功不代表业务验收完成。

不兼容旧请求和快照格式，不导入、回填或删除历史业务数据。数据库沿用任务、关联、认领及 JSON 快照实体，无额外表结构迁移。旧生产数据应留存备份并使用新库部署。

## 2026-10-13 独立开发入口

开发空间同时提供「从项目事项」与「手动开启」。事项入口保留认领／指派、待开发、合并及明确启动流程；手动入口创建当前项目中本人的独立开发任务，不关联事项或发布版本，不提供保存待开发。输入标题、目标／验收条件或图片、实时远端分支及执行设置后，点击启动直接进入会话。

手动开发目标复用新建需求的 Markdown 编辑器，支持写作、源码、预览及图片粘贴。图片使用稳定的 `manual-image:` 引用，预览对象 URL 仅存在于当前表单；图片上传失败需重试或明确忽略后才能启动。项目事项任务选择起始分支时同时提供模型、思考强度和执行权限，选项从当前个人开发空间读取；刷新保留草稿，切换任务重置草稿，启动时冻结执行选择。

启动意图仍须持久化以防重复执行；未知结果只查询原记录，不自动重试派发。独立任务保留初始目标快照、执行人与会话身份，项目任务列表明确显示来源，后续目标在原会话中补充。无需数据库结构迁移，不改动已有 session、source 或 Worktree 路径。

「返回项目协作」移至侧栏项目名旁，保留原项目返回地址。工作台使用顶部账号导航下方的剩余视口高度，页面外层不滚动，会话消息、任务列表及长表单各自在所属区域滚动。

## 2026-10-14 职责与流程动作

本轮已用明确的提报、业务、开发、QA、验收和关注职责取代模糊参与人。系统流程节点新增职责/类别，连线支持资料与最新交付验收门禁，并创建可审计的串行处理动作。交付指定验证人，支持开始验证、转派、退回和重提；版本归档也检查未完成的交付验证。此段与[流程动作契约](../engineering/workflow-actions.md)取代本文较早的人员和工作台描述；全局流程归属暂未改变。
