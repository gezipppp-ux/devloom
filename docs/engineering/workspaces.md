# Project development spaces and execution workspaces

Production ownership and storage follow [accounts-and-database.md](./accounts-and-database.md). PostgreSQL is authoritative. A workspace is the execution context of one project member's DevelopmentSpace; it is not a separately created personal project. Existing recorded identities, sessions, source state and directories are preserved. No old-data import or migration is provided.

## Assignment, preparation and configuration

Effective code.operate authorization allocates exactly one space per project/member without cloning. The member explicitly prepares it with their own Git account and a UUID requestId. ProjectServices checks the actual project repository, performs network/Git work outside transactions, then rechecks current account, department, membership, project/repository/credential revisions and request ownership before atomically publishing the workspace and ready status. Failure retains identity and files; retries are explicit. Startup marks dead-worker preparation failed without replaying it or changing live workers.

Repository checks and cloning classify Git failures into fixed messages for authentication rejection, missing/inaccessible repositories, forbidden access, organization SSO, DNS, connectivity, TLS and redirects. Raw stderr, server response bodies, remote URLs and credentials never appear in these messages. Unknown failures retain the generic fallback. Host login success alone does not establish repository access; a saved failure is historical and is not changed by a later successful read-only check. Regression coverage uses local HTTP Git failures for both ls-remote and clone.

The stable member root is <memberStorageRoot>/projects/<directoryName>/members/<username>; each accepted preparation uses its repository-<preparationRevision> child, and tasks use worktree/<prefix-up-to-16>-<12-hex-task-id>. The persisted space revision identifies each preparation attempt: the same request never reclones, and an explicit new request after failure gets a fresh directory while retaining failed files. Ready spaces keep their recorded repository path. Project creation reserves and persists directoryName from the Git repository basename, stripping .git. directoryKey is its lowercase unique key on all platforms. Later collisions append an eight-hex project-ID suffix (with a counter if needed), truncating the basename to keep the directory at most 120 characters. Archived projects retain reservations. Concurrent reservations retry only the database-only project create/update transaction, at most three attempts. Changing the remote before allocating any space reassigns the directory only if the basename changes. Member names use the canonical login username, with portable encoding for reserved device names; login usernames cannot be renamed. Display names are independent of directory names and authorization still uses IDs. Branches use codex/<12-hex-task-id>; the digest includes canonical repository, full workspace UUID and source identity. Refuse existing task directories or branches. Changing display names, installation directories or system defaults never moves recorded paths.

Project configuration includes initCommands and manual prompt templates. Updates with project.configure and current revision synchronize published workspace configurations. The internal version-6 configuration binds workspace.project_id and workspace.owner_user_id, records workspace.owner_username and execution.projectName (the assigned directoryName), and stores prompt_templates. Project configs from older versions are rejected, with no UUID path fallback. The directory migration rejects databases containing historical projects, workspaces or runs; use fresh data and leave existing files untouched. New runs and newly prepared addition batches capture the current settings; recorded prompts, sessions, branches and paths remain unchanged. Template overrides support manual; null removes an override, required placeholders remain mandatory. Project configuration DTOs require project.configure.

WorkspaceManager owns lazy contexts, channels, RunStore and SessionManager; it does not own project permissions or catalogue data. ProjectServices authorizes the current user and development-space binding before context access. Each context retains independent execution and subscription state. Account credential revisions are read before new transport use; idle connection replacement waits for all preparation, approvals, turns and commands, preserving sessions and never replaying uncertain work.

## Development branch selection

Projects and issues do not store default or suggested development branches. Planning and assignment require no Git credentials or prepared space. A planned task starts only through its explicit start endpoint: the executor selects a branch from GET /api/projects/:id/branches, fetched live with their own credentials. ProjectDevelopmentServices freezes that selection in the accepted task snapshot; missing branches never fall back to HEAD or local cached refs. See [the lifecycle PRD](../prd/project-lifecycle.md).

Every new run persists preparing intent, then holds the shared Git operation lock across origin fetch, SHA resolution, plan persistence and worktree creation. The Git module verifies the saved remote URL, uses the member account, fetches the explicit refs/heads branch, and returns `{remote,branch,commit,fetchedAt}`. The worktree planner receives that fixed SHA; worktree.base_commit and worktree.baseline record the same commit. No pull or source checkout mutation is performed. Failure, cancellation, missing branches or revoked authorization cannot reuse cached refs. Failed preparation remains readable with no invented worktree path; repeated requests never replay the operation.

Worktree creation and Windows path preflight run asynchronous Git processes; large tree listings are read in bounded asynchronous batches. Each Git command retains a 60-second timeout. Cancellation or timeout stops the process tree (including checkout filters/hooks) and waits for Git to close before releasing the repository lock. Authorization is rechecked before creation and after it completes, before initialization or Agent startup. Failed/interrupted creation preserves its recorded plan and any remaining files/refs for inspection; it never deletes or automatically retries them.

Continuation and additional issue batches retain the original baseline and session. Project task DTOs expose the selected task baseBranch, fetched baseCommit and fetchedAt without exposing another member's personal session details. No old baseRef fallback is provided; recorded worktree paths and identities stay intact.

## API and navigation

- GET /api/projects lists authorized memberships; POST creates a project for an eligible creator in an allowed active department.
- GET/POST /api/projects/:id reads or revision-updates project settings; members, archive and restore use their own project permissions.
- GET /api/projects/:id/space returns the current member's assigned space; POST /space/prepare accepts {gitAccountId,requestId} and returns the persisted preparation state.
- GET /api/bootstrap and /api/workspaces list only the current user's ready, code-viewable spaces, including projectId and permissions. POST /api/workspaces and the old personal clone routes are closed in production.
- /api/projects/:id/tasks explicitly starts project development. Direct production POST /api/workspaces/:id/runs is closed.
- Existing session, refs, file, repository, models, approvals, images and SSE routes remain under /api/workspaces/:id. Viewing, starting, continuing, approving, stopping and code operations have distinct current permissions. Production workspace settings/name writes are closed; use project configuration.
- SSE checks current login, ownership and session.view on connection, frames and heartbeats. Revocation closes subscriptions; execution revocation aborts preparation or requests an interrupt without deleting data or pretending the engine has stopped.

The Web default page is the project list; /projects/:projectId shows collaboration. An explicit workspace query opens its execution console. Switching consoles preserves URL identity and recreates scoped request/subscription state; late responses cannot cross accounts or spaces. The injected manager/testIdentity server option remains an explicit isolated test harness, never a production compatibility route.

## System directories and Git

GET/POST /api/system/settings are administrator routes for the one memberStorageRoot and Git environment information. PostgreSQL owns the setting. Require an absolute writable service-host path and save its canonical real path. GET /api/system/directories offers bounded server-side directory browsing. New tasks reload system defaults, while existing repository and task paths remain recorded. CLI explicit non-workspace configuration retains its own root selection.

Cloning rejects existing targets and symlink ancestors, claims the target exclusively, and preserves failed project preparation files. Worktree creation validates the member boundary and complete plan. Windows checks tracked-file and checkout-directory UTF-16 lengths before creating branches/directories; it does not alter OS/Git long-path settings or guarantee future build-output lengths.

Git accounts bind host/protocol and belong to the member, independently of repository selection. Saving is local validation; explicit connection checks require a permitted project and test its actual repository. Credentials never appear in remote URLs or DTOs. HTTP secrets are injected only into the child process; SSH keys use restricted temporary files. Explicit author name/email are separate from login identity. Referenced accounts cannot change host/protocol or be deleted.

Public Gitee repositories support equivalent HTTPS and SSH clone addresses on default ports. ProjectServices and GitAccountServices resolve the selected account's transport using the same domain rule, retaining the owner/repository path. Prepared workspace `execution.remoteUrl` records that actual clone address; project settings synchronization preserves it. Custom hosts, ports and SSH users are not guessed or converted, and credential ownership checks remain mandatory.

## Codex model, reasoning and permissions

`GET .../models` reads the current workspace client's `model/list` with pagination. Expose only model ID, display label, supported reasoning efforts, default effort and `isDefault`. Filter hidden models; reject malformed pagination. Discovery never starts a thread/turn or closes the shared client.

The project development task start endpoint accepts optional `model`, `reasoningEffort` and `permissionMode` strings. Each new requirement form defaults to blank model/effort (local Codex defaults) and `ask` permission. The linked dropdowns retain current draft values on discovery failure, allow retry, and clear an unsupported effort when changing model. An explicit effort requires a concrete model. Every submitted explicit selection is validated against the catalog before resolving the channel or claiming a run; blank model/effort is resolved against effective config and catalog defaults before starting a turn. Unsupported combinations and invalid types are rejected.

Workspace settings neither expose nor accept model/effort. Old workspace values are ignored when starting Web tasks and removed on the next project settings save; existing run snapshots remain untouched. New Web runs snapshot model, reasoning effort and permission mode in `run.json.codex`. Subsequent choices live in `execution-settings.json`, with current and next-turn semantics defined in [web-cli.md](./web-cli.md). Each new turn explicitly sends resolved model/effort and selected approval/sandbox settings on the same thread. Run summaries retain the original `codex` model/effort for context and expose current choices separately as `executionSettings`, `activeExecutionSettings` and `settingsPending`. CLI supplies `-c model_reasoning_effort=...` as an argument for explicit CLI configuration. Verify same-workspace task isolation, defaults ignoring stale settings, invalid selections, offline discovery, manual input, active-turn staging and continuation after reconnect.

## Removed channel

TAPD import, search, task creation, fusion and source-append endpoints are removed. Project and workspace settings do not expose its credentials or templates, and new settings payloads reject retired keys. Stored historical source identities and snapshots remain readable without registering an adapter or contacting the source.

## Repository updates and Worktree deletion

### Read-only session files

- `GET .../runs/:key/files?scope=task|head` lists changes against the recorded `worktree.base_commit` or current HEAD, including untracked non-ignored files and rename metadata. `GET .../runs/:key/file?path=...&scope=task|head` resolves a local reference and returns current/baseline text, bounded hunks, or explicit unsupported-content reasons. Basename-only ambiguity returns candidate paths without content. Absolute paths must remain inside the recorded worktree; relative paths never select another repository.
- `SessionFiles` checks task existence/deletion before and after reads; the HTTP workspace ownership gate applies unchanged. The Git module verifies registration/common-directory/backlink and rejects symlink/junction ancestors and file components. Only paths listed by Git in the current index/non-ignored files or selected base tree are eligible; `.git` and traversal are rejected. Reads never claim a Codex session, execute turns, mutate refs/index, or fetch remotes. Responses use `no-store`.
- Use fixed resolved commit IDs during a read and reject a changed HEAD/worktree. Working text is a read-time view, not a turn snapshot. No missing-base fallback: current source remains available, while task comparison reports its unavailable baseline. Deleted worktrees remain unavailable even if a directory reappears.
- Bound Git queries to 10 seconds / 4 MiB, catalogs to 20000 entries, and each source/baseline to 512 KiB / 10000 lines. Refuse binary/non-UTF8/symlink/submodule content. Diff calculation has a time/edit bound and normalizes CRLF to LF only for line comparison; returned source text is preserved. Never report an incomplete read as no changes.

### Repository mutations

All Git endpoints remain workspace-scoped and use the standard Host/Origin and POST token protections. No endpoint accepts arbitrary repository paths, remote URLs or Git commands. Repository operations use the saved workspace repository; task operations use the recorded original repository/path/branch, even after workspace settings change.

- `GET .../repository/git` returns repository, baseBranch, branch, remote, named remotes, upstream, canUpdate, updateReason and lastFetchedAt/lastFetchedRemote. Remote URLs and credentials are not exposed.
- `POST .../repository/git/fetch {remote}` fetches/prunes only an existing remote. `POST .../repository/git/update {remote?}` fetches the configured upstream and updates the currently checked-out local base branch with `--ff-only --no-overwrite-ignore`. Omitted remote uses that branch's configured remote. Reject dirty/untracked files, detached/non-current/non-local bases, Git operation markers, locks, missing upstream, changed HEAD during fetch and divergence. Never switch, stash, reset, force-push or create a conflict-resolution workflow. Network commands run asynchronously with timeout and interactive credentials disabled.
- `GET .../runs/:key/git` returns the recorded task `branch` and the live `currentBranch`, path, HEAD, upstream, unpublished, ahead/behind, changedFiles, untrackedFiles, ignoredFiles, clean, statusToken, canDelete and deleteReason, plus recorded deletion progress. changedFiles counts tracked files; the UI adds untrackedFiles for the uncommitted total. Ignored entries may be directories. No remote upstream (including tracking a local branch) means unpublished and null counts. A deleted remote upstream returns unknown counts and a warning; an otherwise verified task can still be removed after explicit risk acknowledgement. Other Git/identity read failures block deletion, never report zero. Refreshing status does not fetch or start Codex.
- `POST .../runs/:key/worktree/delete {expectedHead,statusToken,confirmBranch,discardChanges}` deletes the recorded task Worktree and its local branch. Require full branch-name confirmation and a fresh snapshot. Local/unpublished/unpushed/ignored content requires explicit discard acknowledgement. Reject active/preparing tasks, pending requests, execution locks, another service owner and a Codex session that cannot be verified idle. Claim session ownership and serialize mutations by the real shared Git common directory across workspaces/processes.

The Git-panel deletion verifies the original Git worktree registration, branch, common directory and backlink, rejects the main checkout, symlink replacements, locked worktrees and unfinished Git operations. Confirmation fingerprints include descendant metadata inside ignored directories without following links. Scanning is bounded; when a complete fingerprint cannot be produced, preserve already verified Git status and disable deletion with a reason rather than accepting a partial token. This endpoint uses `git worktree remove`, followed by local branch deletion, without a recursive filesystem fallback. Never delete remote branches or infer that task progress is complete.

Continuation verifies the recorded Worktree directory, Git registration, common directory and backlink, but intentionally follows the directory's current checkout rather than requiring its recorded initial branch. Git registration matching compares physical paths when recorded and registered spellings differ (including macOS `/var` and `/private/var`); it never rewrites saved session paths or ignores case globally. Missing paths stay read-only, and the common directory, backlink and deletion symlink checks still apply. Switching branches in that same verified directory therefore remains writable; the Git panel refreshes and displays the live branch. A branch switch disables destructive Worktree deletion until the recorded task branch is restored, so cleanup can never delete a different branch.

Persist intent and progress in `worktree-deletion.json` separately from immutable run/session identities. Directory removal and branch deletion are separate recorded stages. Partial cleanup can retry only while the original path remains absent, the branch is not checked out elsewhere and its HEAD still matches the recorded deletion. Restart recovery handles a persisted intent whose directory removal completed before the progress write. Reappearing paths or changed branches block recovery. Deleted tasks remain visible with history/materials and a read-only reason; resume, images and execution-setting writes are rejected even if someone later recreates the old path. Scoped SSE announces deletion so other tabs refresh.

Session archive is independent of Worktree deletion: archived sessions are excluded from ordinary sidebar lists but retain their records and code. Permanent session deletion requires explicit confirmation; by default the recorded Worktree/local branch must already be removed. The optional `force:true` plus exact `confirmBranch` performs code cleanup in the same session operation before deleting records, snapshots, history, logs and attachments. The UI displays the full recorded directory and branch and explicitly confirms loss of dirty, untracked, ignored and unpublished/unpushed content. Force cleanup skips content fingerprint scanning, tries targeted `git worktree remove --force`, and may recursively remove remaining files only inside the validated recorded absolute task directory. It rejects filesystem roots, the main checkout or its ancestors, paths containing other registered worktrees, symlink/junction replacements (including ancestors), switched/locked worktrees, unfinished Git operations and branches checked out elsewhere. An intact Git marker still requires original repository/backlink verification; missing directories or unregistered leftovers may be cleaned after the path/branch checks. Persist directory identity and cleanup progress; a replaced or reoccupied path is not authorized by an earlier attempt. Remove stale registration only for the specific task, never by globally pruning other worktrees. Preserve the session on any failed stage, and await outstanding completion/history writes before deleting its data so delayed responses cannot recreate it. Active tasks, pending requests, foreign Web owners and uncertain Codex state still block forced code deletion.

The Web app has no merge or conflict-resolution button. Users instruct Codex in the existing task session when they want merge/conflict work.

## Development state and deliveries

Personal sessions have execution state and a display title; they do not store manual type/progress metadata or grouping preferences. The metadata endpoint, SSE event and catalog have been removed without compatibility readers. Development task lifecycle and issue workflow stay independent of Agent execution.

The development entry offers independent development and issue development. Session switching uses a picker; context starts closed. Code changes open a full workspace with a file list, cumulative/uncommitted comparison and return to the unchanged conversation draft.

Project deliveries use POST /api/projects/:projectId/deliveries. Supply an issueId or a taskId for an owned, started independent task. Task references must match project, owner and issue scope. Read/review paths remain /deliveries/:id and /deliveries/:id/review. Review requires deliverable.review; an optional issue transition is authorized separately. Private completion uses the existing task complete action, with revision and execution-idle checks.
