# Web CLI contracts

> Production HTTP now uses authenticated Fastify sessions and private workspace authorization; history reads PostgreSQL. See [accounts-and-database.md](./accounts-and-database.md). Historical JSON/JSONL references below name logical record types or explicit fixtures. The execution, Git identity and channel transition invariants continue to apply.

> 工作区版：参见 [workspaces.md](./workspaces.md)。生产 Web 的 API 均在 `/api/workspaces/:workspaceId` 下，配置/运行/上传/事件独立。本文旧全局路径仅对应单管理器测试及显式 CLI 配置，不是数据迁移约定。


## 1. Scope / trigger

Applies to `src/codex/app-server-client.cjs`, `src/application/session-manager.cjs`, `src/storage/run-store.cjs`, `src/http/server.cjs` and `web`. The Vue console consumes the normalized Agent API. The Codex provider uses app-server JSON-RPC; application services do not handle native RPC. See [Agent contracts](./agents.md), which supersede the protocol-specific descriptions below at the application boundary.

Process startup lives in `src/cli/web.cjs`. The HTTP module exports an inert server factory and adapts application services. Session commands, event handling, queries and public response shapes are separated in `src/application/`; disk formats remain in `RunStore`, and repository/worktree identity checks live in `src/git/`. Shutdown stops accepting requests before closing SSE and session managers, so EventSource reconnections cannot keep the service alive.

Closing a session manager fences in-flight validation/resume/start operations, drains already-started channel callbacks and transport shutdown, then releases ownership. `AppServerClient.close()` is terminal; accidental disconnects can reconnect. A completed first turn cannot start another turn until the execution runner finishes persisting its result and releases its lock; steering an active first turn remains supported.

Git credential revisions are checked before starting or sending when the entire workspace is idle. Active turns, approvals, preparing pipelines and in-flight startup/command operations fence connection replacement. A credential refresh disconnects only the idle transport; continuation resumes the same recorded thread. Each reconnect loads fresh credentials and releases old temporary identity/key files only after their child has stopped.

A delayed first `turn/start` response must still belong to the original startup operation and must not restore a turn already marked completed, including while database history reconciliation is pending.

## 2. Signatures

- `npm run build` builds the assets; `npm start -- [--host 0.0.0.0] [--port 4317]` starts HTTP. CLI startup defaults to `0.0.0.0` for direct IPv4 LAN access; `--host 127.0.0.1` limits access to the local machine. `--config` is rejected by Web startup.
- `npm run dev -- [--host 0.0.0.0] [--port 5173]` serves Vite HMR, API and SSE through one HTTP server, retaining origin and token checks. Development defaults to all IPv4 interfaces for direct LAN IP access; `--host 127.0.0.1` limits access to the local machine. Development also accepts port `0` for an ephemeral port. `npm run dev:watch` accepts the same arguments and defaults and restarts this child after backend CJS/shared JSON changes, requesting shutdown over IPC before replacement. A backend restart interrupts active turns and initialization, preserves recorded identities, and lets Vite reconnect and reload the page with a fresh bootstrap token. It never automatically resumes or redispatches a requirement. Frontend HMR alone does not restart the backend. Production startup, CSP and static assets remain unchanged.
- `GET /api/bootstrap` returns `{token,workspace,channels}`; `GET /api/runs` returns `{runs}`.
- In explicit test harnesses, `POST /api/runs {channel:'manual',requestId,title,content,images,model?,reasoningEffort?,permissionMode?}` creates a task after validation. Production uses project development task endpoints.
- `GET /api/execution-options` returns `{permissionModes:[{id,label,description,available,reason?}]}`. Permission IDs are `ask`, `auto`, `full`; omitted creation permission defaults to `ask`.
- `POST /api/runs/:key/execution-settings {model?,reasoningEffort?,permissionMode?}` saves a validated patch and returns `{executionSettings:{model,reasoningEffort,permissionMode},pending:boolean}`. Reject unknown fields, invalid values and unsupported native auto review.
- `GET /api/runs/:key` returns normalized history, live overlay, requests, status, readOnlyReason, images, requirement and nextCursor. Detail and list also expose `executionSettings` (next-turn selection), `activeExecutionSettings` (active turn selection or null), and `settingsPending` (an active turn uses different settings). `requirement` contains full saved description/Markdown/prompt, source URL, captured timestamp, safe image routes and snapshot fallback warning; never expose the whole task JSON or credentials. `GET .../history?cursor=` returns `{items,nextCursor}`.
- `POST .../messages {text?,images?:string[]}` sends or steers. Text is at most 60000 characters; either nonblank text or at least one image is required. `images` contains at most 20 distinct image IDs uploaded to this run. Existing text-only clients remain compatible. `POST .../interrupt {}` stops the current turn.
- `POST .../message-images` uploads a raw PNG/JPEG/WebP body of at most 10 MiB and returns `{id,name,size,contentType,url}`. `GET .../message-images/:id` serves the recorded attachment in the same workspace/run. Uploading does not start or resume a Codex turn.
- `POST .../responses {requestId,decision:'accept'|'decline'}` or `{requestId,answers:{questionId:text}}` resolves a pending request.
- `GET /api/events` is SSE; `GET .../images/:index` serves only recorded images under the run directory.

## 3. Contracts

- `key` is the validated run identity: a channel-prefixed hash of the explicit source scope/ID for new runs. Recorded keys are opaque and are not rewritten. Browser callers cannot submit arbitrary thread IDs. Explicit execution settings accept validated service-host paths; run/image paths remain bound to recorded runs.
- Every POST requires `x-csrf-token` from bootstrap. `src/cli/web.cjs` defaults to `0.0.0.0`; the `createWebServer()` HTTP factory retains `127.0.0.1` as its internal default for embedding and tests. Explicit `--host` accepts an IPv4/IPv6 literal, including wildcard binds. Validate the Host IP and port against the request socket's local address/port (normalizing IPv4-mapped IPv6), require any Origin to match the validated HTTP origin, and reject cross-site fetches. Forwarded headers never authorize a Host. JSON bodies are bounded to 256000 bytes with streaming UTF-8 decoding; messages are 1–60000 characters.
- Transport initializes with `initialize` then `initialized`; IDs correlate concurrent RPC. Guard child-process listeners by child identity so closure of an old connection cannot kill its replacement.
- Initialize with `capabilities.experimentalApi: true` to receive experimental `item/tool/requestUserInput` requests, independently of model names. Validate question IDs, text and options before exposing them; answer every question explicitly using `{answers:{questionId:{answers:[text]}}}`. No default choice or timeout submits an answer. Keep legacy requests without `isBlocking` blocking; only a user-input request with `isBlocking:false` permits steering and message image uploads while pending. Approval requests always remain blocking. Reject foreign/stale turns and malformed questions; scoped `serverRequest/resolved`, turn completion and disconnect clear pending input. The native question dialog shows headers, option descriptions, free text and masked secrets, retains drafts when collapsed or a submission fails, and supports Escape/reopen and narrow screens. A page reload restores pending questions from the live runtime, not answered drafts. Answers are forwarded on the original RPC ID without being added to application logs.
- Existing threads use `thread/read` then `thread/resume` with the recorded cwd and selected permissions. New runs inject `startSession` into `runExecution`; `thread/start` returns identity, but only `turn/started` authorizes channel transition.
- Permission mapping is centralized in `codex/permissions.cjs`: `ask` uses `on-request`, reviewer `user`, sandbox `workspace-write`; `auto` uses `on-request`, reviewer `auto_review`, the same sandbox; `full` uses `never`, reviewer `user`, sandbox `danger-full-access`. Each `turn/start` explicitly sets approval policy, reviewer and `sandboxPolicy`, so reducing permissions does not inherit a previous full-access turn. Limited turns use the recorded worktree as writable root and disable network access. Native Codex remains responsible for enforcement and any managed policy restrictions.
- Confirm `auto_review` support by generating the installed executable's stable protocol schemas, checking start/resume/turn fields, and caching by executable identity. This read-only discovery never creates a thread or executes a requirement. Failure disables `auto`; never substitute automatic acceptance of browser approval requests.
- Save execution preferences in `execution-settings.json` as `{selection,active}` through RunStore atomic writes. Preserve the creation snapshot in `run.json.agent`, session identity, explicit source and recorded paths. Missing preferences use the original Agent selection; old provider fields are not read. Session ownership and the same command mutex protect setting changes; refuse removed worktrees, foreign owners and preparation/initialization.
- Settings changes during a running turn or pending approval only save the next-turn selection and publish `execution-settings` SSE. They do not resolve approvals or interrupt/steer a turn. Supplementary instructions use `turn/steer` with no settings parameters. The next `turn/start` applies the latest saved settings on the same thread/worktree. Clearing a model/effort resolves the effective native config or catalog default into concrete turn values, because omitted/null fields can retain prior thread overrides. Fail visibly if defaults cannot be resolved.
- New Web runs validate the Codex executable before claiming ownership or preparing a worktree. Changing a worktree root does not remove existing Git branches or stale registrations. Branch conflicts must preserve previous work and explain cleanup; never force-delete/reuse a branch or redispatch an uncertain run automatically.
- During `initializing`, SSE command items expose live worktree initialization output; snapshots restore them from `run.json` even before a Codex session exists. Sending messages stays disabled. Interrupt aborts the initialization process tree and service shutdown aborts pending preparation. Failed initialization never dispatches Codex or transitions the source. No initialization executes when saving settings or resuming an existing session.
- Input is `[{type:'text',text,text_elements:[]}, ...{type:'localImage',path}]`, omitting the text part for image-only messages. Active turns use `turn/steer` with `expectedTurnId`; subsequent turns use `turn/start` on the original thread. Stop uses `turn/interrupt`.
- Conversation attachments are channel-independent and persisted under the owning run, separately from the original requirement snapshot. Accept only server-generated image IDs belonging to that run, never browser-supplied paths or URLs. Uploads and sends respect session ownership, preparation, read-only state and pending approvals. History and SSE expose attachment URLs through the application presenter, preserving images on refresh and reconnect without exposing arbitrary local files.
- The composer accepts clipboard image files and file selection, previews/removes attachments, and supports image-only sends. Ordinary text paste keeps native textarea behavior. Enter sends, Shift+Enter inserts a newline, and IME confirmation or repeated keydown events never send. Uploading or failed attachments block both the send button and Enter until resolved; upload retry and failed sends retain the draft. Async uploads and successful sends stay scoped to the original workspace/run selection and cannot mutate a newly opened draft.
- History uses `thread/items/list {threadId,limit:50,sortDirection:'desc',cursor?}`. Reverse each page for chronological rendering. Preserve pagination cursor when refreshing an expanded history.
- Snapshot history defines the visible page and chronological order. Runtime overlays update overlapping items and append new items without moving saved items from older pages behind the latest messages.
- The conversation presents adjacent ordinary activity from the same known turn as one collapsed summary, including running commands. Messages, plans, unknown item types and failures remain separate; missing turn IDs never authorize cross-record grouping. Nonzero exits and item errors remain visible outside the fold. Expansion is scoped to the selected session and retained across streaming updates and history pagination; canonical records and pending approval/question controls are unchanged.
- SSE events have `{key,at,type,status,sessionId,turnId,...}`; `item` contains a normalized item; `requests` contains currently valid server requests. Reload fetches canonical history plus live items; pending approvals are never silently replayed after disconnect.
- The browser ignores superseded view/list responses and preserves newer SSE fields, metadata and items received while a snapshot is pending. Initial selection follows the same rule, and history pagination remains scoped to its selection. A delayed snapshot must not resurrect an ended turn or an already resolved approval.
- A session title is a trimmed, nonempty display override of at most 200 characters. It is stored separately from the requirement snapshot and `run.json`, emitted as a title-only SSE event, and never changes the session ID, branch or Worktree path.
- `GET .../runs?archived=true` lists only archived sessions in the authorized workspace, with `archivedAt`, newest archive first; ordinary lists continue to exclude them. `POST .../runs/:key/restore {}` clears the archive marker idempotently and emits a scoped `restored` event. Restore only changes list visibility, retaining title, session identity, history and Worktree deletion state; it never starts Codex or recreates code. Permanently deleted records cannot be restored. The sidebar archive dialog supports search, retry, restore and direct permanent deletion using the same confirmation window and delete endpoint as the session page, including optional forced code cleanup. Its deletion target stays mounted independently of list refreshes and early SSE events until the request finishes; cancel returns to the same search, and stale list responses cannot resurrect deleted rows. The list refreshes on scoped events/reconnection and ignores superseded snapshots and unmounted requests.
- The personal development queue supports selecting individual rows or all eligible rows on the current page. Planned tasks retain merge actions; owned sessions with `session.continue` also offer batch archive through the existing workspace-scoped archive endpoint. Confirmation lists the selected sessions and preserves per-session failures for retry without resubmitting successful rows. Archived sessions are excluded from `/api/workbench/tasks` before pagination/counting and return after restore; project task history and business task status remain unchanged. The archive browser entry is labeled “查看已归档会话” (View archived sessions).
- `POST .../runs/:key/archive {}` archives an idle session: it remains readable by direct record access but is omitted from ordinary session lists, and it does not remove any history, attachment or Worktree. `POST .../runs/:key/delete {confirm:true,force?,confirmBranch?}` removes all run documents, history, logs and attachments. The default requires prior Worktree/local-branch cleanup. Explicit `force:true` with the exact recorded `confirmBranch` first removes the recorded Worktree, local directory (including uncommitted/untracked/ignored files) and local branch regardless of unpublished/unpushed content. It still rejects active/pending sessions, other Web owners, unsafe paths and uncertain Codex state. Completion/history writes must settle under the session operation lock before clearing data. Failed code cleanup retains the record and progress for retry. Both archive and deletion emit scoped list-removal SSE events; pending list snapshots must not restore removed rows or older titles.
- Render Codex replies as Markdown, including streamed updates and saved history, through `message-content.js` and a DOMPurify allowlist. Support headings, lists, code blocks, tables and safe HTTP/HTTPS/mailto links; show raw HTML literally and image alt text without loading Markdown image URLs. User messages and tool output remain escaped plain text. Bound long text/output. `web-events.jsonl` stores item metadata rather than duplicating the whole growing output for every token.
- Local Markdown file links and filename-shaped inline code render as sanitized buttons, never direct filesystem URLs. `file-reference.js` retains absolute/relative paths and `:line[:column]` / `#Lline` positions; the server authorizes and resolves paths. Native buttons provide keyboard activation and emit requests through the session shell. Raw HTML cannot forge a file button; safe external links retain their existing behavior. The code panel owns scoped request generations, clears late results after switching/closing, and never changes draft/session identity. File preview is current worktree content; per-turn snapshots are not implied.
- Requirement details are a deliberate full-content exception to output truncation: read only requirement.json, and show run.workitem with a visible warning if the task snapshot is missing/corrupt. Render Markdown/HTML only through the dedicated DOMPurify allowlist; remove scripts, frames, event handlers and styles, allow only safe link protocols, and replace image sources with validated local task image routes. Unmapped images refer readers to local attachments and must not trigger remote requests. Full Codex prompt remains escaped text. Browser regressions cover unsafe HTML, local images, Markdown and missing/current snapshots; store tests protect long content from truncation.
- Preserve CLI `run.json`; execution and source transition are independent. `web-session.json` holds Web metadata. Validate original Git worktree registration, repository identity and `.git` backlink before continuation; continuation follows the directory's current branch. `web-owner.json` fences other Web processes; `.lock` fences legacy CLI ownership.
- Serialize `run.json` mutations with the short-lived `run.json.lock` directory. Continuation updates only execution fields; channel synchronization updates only transition fields against the latest saved record, including transition-only CLI retries. Use unique temporary files and atomic rename. Never hold this write lock across network calls. A lock left by a crashed writer fails closed with its path; remove it only after confirming all writers have stopped.
- Reclaim dead Web owners under the exclusive `web-owner-recovery` guard, rereading ownership inside it. A leftover recovery guard also requires checking stopped services before cleanup. Continuation must verify the target directory's actual Git common directory and worktree backlink, not just a stale registration. After awaiting initial channel synchronization, completion handlers must still belong to the current turn before updating runtime or execution state.

## 4. Validation & error matrix

### Historical requirement additions

- Source append is removed. Previously saved additions remain readable and may be explicitly continued on their recorded session without fetching external materials.
- `POST .../runs/:key/requirements/continue {id}` explicitly sends one saved addition as a new turn on the original session/worktree. Persist `sending` immediately before the RPC, `sent` with its turn ID after acknowledgement, and `uncertain` when acknowledgement is lost. Pre-dispatch validation failures leave the addition `ready`. A repeated sent request returns its result; `sending`/`uncertain` never replay automatically, including after restart. Addition pictures are also persisted as conversation images so native history image representations remain readable.
- Original requirement snapshots remain immutable. Public requirement DTOs add `requirements` for ordered initial sources and `additions` for later batches; each source retains sanitized rendering and scoped local image routes. `GET .../runs/:key/addition-images/:id/:index` only serves images referenced by committed additions. The `requirements` SSE event carries the current requirement projection and source count; pending snapshots must preserve that newer event.

| Condition                     | Result                                        |
| ----------------------------- | --------------------------------------------- |
| Removed/unregistered worktree | History readable, mutations refused           |
| Active external CLI/Web owner | No concurrent resume/start                    |
| Unknown/expired request ID    | No response forwarded                         |
| Unsupported server request    | JSON-RPC error, visible UI error, no approval |
| Wrong origin/token            | HTTP 403                                      |
| Invalid body/fields           | HTTP 400                                      |
| Missing run/asset             | HTTP 404                                      |
| RPC timeout/disconnect        | Explicit error, no automatic redispatch       |
| History unavailable           | Warning with legacy CLI event fallback        |

## 5. Good / base / bad cases

- Good: interrupt turn A, send another instruction, start turn B in the same thread/worktree.
- Base: open completed CLI history without resuming or executing anything.
- Bad: a leftover folder after Git worktree removal must not authorize continuation in the root checkout.

## 6. Required tests

`test/integration/web-sessions.test.cjs` covers RPC correlation, process exit/reconnect, same-thread followups, live deltas, steer/interrupt, startup ordering with images, questions/approval, worktree/ownership fences, pagination and HTTP UTF-8/origin/token/SSE. `session-settings.test.cjs` additionally covers setting validation, staging, permissions, persistence, identity preservation and write failures. `test/browser/session.test.cjs` uses a fake protocol client and real built page to exercise send/steer/stop/continue, requests, next-turn settings, reload and mobile layout. Runner tests verify execution ordering and transition retry isolation.

## 7. Wrong vs correct

Wrong: create a fresh session on every browser message, or change external business status during execution.

Correct: retain `session_id`, resume it once, submit turns on that ID, and call the runner's `onStarted` only from an actual `turn/started` notification.
