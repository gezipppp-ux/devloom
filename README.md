# Web Coding · 需求开发工作台

Node.js 22.13+、Vue 3 的本地需求开发工作台。**一个工作区对应一个项目和一套独立配置**，支持 TAPD 需求和手动图文需求；每个任务拥有独立 Git worktree 与持久化 Codex 会话。

## 开始使用

需要 Node.js 22.13+、npm、Git，以及已安装并登录的 Codex CLI（`codex login`）。

```sh
npm ci
npm run tapd:web
# 已构建时，默认监听所有 IPv4 网卡
npm start -- --port 4317
# 仅允许本机访问
npm start -- --host 127.0.0.1 --port 4317
```

本机打开 `http://127.0.0.1:4317`，局域网电脑打开 `http://<服务端IP>:4317`，创建工作区，然后填写项目的 Git 仓库绝对路径、worktree 根目录、基准引用和可选初始化命令。路径属于服务端主机；不自动克隆仓库。

最左侧的图标栏用于切换工作区，悬停可查看完整名称，点击「＋」新建工作区。相邻侧栏显示当前项目和需求列表，项目名旁的「…」可编辑名称和图标，下方提供工作区设置入口。图标可从 40 个常用 SVG 图标中搜索选择（支持中英文关键词），也可恢复为名称首字；新建工作区时同样可选。窄屏时图标栏变为顶部横排。工作区选择保存在页面 URL，刷新后保留，不同浏览器标签页可以同时使用不同工作区。切换不会停止原工作区的后台任务。每个工作区只显示自己的会话、需求资料和附件。


这是新的数据结构，**Web 不迁移或读取旧的全局配置、runs 和 uploads**。旧文件可以在停止旧服务后清理。不要把示例配置、源代码或业务仓库当作运行数据删除。

## 工作区设置

每个工作区只有一个目标仓库，所有渠道共用这个项目，不使用按 TAPD 项目映射的多仓库设置。

- 仓库：已克隆的 Git 仓库根目录，服务端绝对路径。
- Worktree 根目录：默认 `~/.codex-workspaces`，可使用其他磁盘或目录。
- 基准引用：默认 HEAD，可选择本地分支、远程跟踪分支、标签或填写 commit SHA；选择器只读本地 refs，不执行 fetch 或 checkout。
- 初始化命令：每行一条，最多 20 条、每条 4000 字符、每条超时 15 分钟。Windows 使用 cmd，Linux 使用 sh。每条从新 worktree 根目录开始，互不继承 `cd` 和环境变量修改；例如 `pnpm install`、`pnpm build`。

保存只影响新任务；已有任务继续使用记录的 session、路径和分支。初始化失败、超时或停止后不启动 Codex、不修改渠道状态，保留目录和日志用于排查。不会自动重跑不确定的初始化或已有任务。

## 在 Web 维护 TAPD

在工作区设置的「TAPD 渠道」中填写：

1. TAPD 项目 ID：与应用工作区 ID 不同，一个应用工作区绑定一个 TAPD 项目。
2. 包含 `dsc-token` 的完整单行 Cookie。
3. 开发中状态码，默认 `developing`；可选额外图片域名，每行一个完整主机名。

「检测连接」用当前填写的 Cookie 和项目调用只读待办接口；Cookie 留空时使用已保存值。检测展示成功或失败，**不保存配置、不启动 Codex、不修改需求状态**。即使待办为空也能检测。网络异常、过期登录或接口拒绝会提示检测失败。

「保存 TAPD 配置」保存后立即生效，无需重启。Cookie 不会回显；留空保留原值，粘贴新值替换，也可勾选清除。配置文件包含凭据，请勿提交到 Git。手动需求不需要 TAPD 配置。

「从需求启动」中检索当前项目的待办，或者直接填写需求 ID；开发和测试人员通过姓名/拼音搜索后选择。TAPD 项目绑定在设置中维护，启动表单只读显示，服务端也拒绝跨项目请求。确认启动即授权本次任务在收到 Codex 实际执行开始后流转为开发中，流转失败与 Codex 执行状态分别保存。

## 每个需求的模型、思考强度与权限

在「从需求启动」中为本次需求选择 Codex 模型和思考强度，TAPD 与手动需求均适用。每次新建需求默认使用 Codex 默认配置，可独立选择不同模型；模型列表实时读取服务端 Codex，加载失败可刷新重试并保留当前选择。

选择具体模型后，思考强度下拉框只显示该模型支持的选项，也可使用默认强度。切换模型会清除不支持的强度。工作区不再设置模型或思考强度，旧工作区中的这两项不影响新任务。

创建需求时同时选择权限，默认「请求批准」：

- 请求批准：使用工作区写入沙箱，写入工作区外文件或访问网络时按需请求用户批准。
- 帮我批准：使用同样的沙箱，由 Codex 原生自动审查权限请求，根据风险决定是否批准；当前 Codex 不支持或能力检查失败时禁用，并显示原因。
- 完全访问权限：关闭 Codex 沙箱与逐次审批，允许访问网络和本机文件。仅在信任当前任务时选择。

会话输入框左下可修改权限，右下可修改模型与思考强度，选择后立即保存。执行中修改会显示「下一轮生效」；本轮补充指令继续使用本轮设置，结束后发送的新消息使用新设置。修改不创建新会话或 worktree，也不会处理已有审批。刷新、重连与服务重启后保留选择；切回默认模型或强度时，下轮会重新读取适用的默认值。初始化中和只读任务不可修改执行设置。

## 手动图文需求

选择「手动输入」，填写标题和 Markdown 内容，可附 PNG/JPEG/WebP 图片，最多 20 张、每张 10 MiB；支持仅标题加图片。上传和运行记录都按应用工作区隔离，不能引用另一个工作区上传的图片。未使用的暂存图片 24 小时后过期，在后续上传时清理。

目录默认按标题生成，英文保留、中文转无声调拼音。可设置 worktree 目录名称，只支持 1–64 位英文字母、数字、短横线或下划线，以字母或数字开头，排除 Windows 设备名；不能传路径，不会覆盖已有目录。

## 类型标签与任务进度

创建任务时可选择「需求 / Bug / 其他」类型，已有任务可在会话顶部修改。左侧列表显示类型标签和进度，支持按类型分组、按进度分组或不分组；分组可折叠，分组方式按工作区在当前浏览器中记忆。

新任务默认为「进行中」。人工进度提供「进行中 / 待验收 / 待合并 / 已完成 / 已搁置」，在会话顶部选择后立即保存。Codex 的执行、停止、单轮结束和重连续聊均不自动修改人工进度，执行状态会另外显示。修改类型或进度只更新本地任务管理信息，不修改 TAPD 状态。

旧任务尚未标记时默认显示「需求、进行中」（原始类型为 Bug 的显示 Bug），可以随时手动调整；不会根据历史执行结果自动认定完成。

## Git 和会话

新任务创建的 worktree 位于：

```text
<worktree 根目录>/<仓库路径哈希>/<应用工作区 ID>/<任务目录名>
```

分支为 `codex/<应用工作区 ID>/<渠道任务名>`。不同工作区即便指向同一仓库、处理同一需求，也不会共用分支或目录。

根仓库不会切换分支、stash、提交或带入未提交的更改；不会复制 `.env`、Cookie 或 node_modules。任务结束保留 worktree。服务不会自动合并、推送、删除分支或验收需求。

Web 使用 `codex app-server --stdio`，按任务选择设置审批与沙箱。需由用户处理的命令和文件审批、澄清问题在页面显式显示。输入框可发送后续指令，执行中可补充指令或停止当前轮；始终沿用原 session。关闭浏览器不停止任务；正常关闭服务会请求中断活动任务，重启后可继续。

会话详情显示历史消息、命令输出、文件修改，以及启动时的完整需求快照、图片和实际提示词。已移除或未注册的 worktree 只读。记录中的路径是权威值，修改安装路径或设置不会搬动业务 worktree。

## 数据与部署

默认数据目录为应用目录，可用 `RUNNER_DATA_DIR` 指定独立位置。静态资源固定从安装包的 `web/dist` 读取。

```text
<RUNNER_DATA_DIR>/workspaces/<应用工作区 UUID>/
  config.json       # 工作区名称、项目执行配置、TAPD 凭据和渠道设置
  uploads/          # 手动需求暂存图片
  runs/<任务 key>/  # run.json、execution-settings.json、requirement.json、images、会话事件和初始化日志
```

`workspaces/` 已加入 Git 忽略。一个工作区一份配置，不共享 Cookie 或执行设置。只有本机 Codex 登录和未覆盖的默认模型来自服务用户的 Codex 环境。

CLI 启动默认监听 `0.0.0.0`（所有 IPv4 网卡），通过 `http://<服务端IP>:4317` 访问；可用 `--host 127.0.0.1` 限制为本机访问。Host 须匹配实际连接的服务端 IP 和端口，Origin 须同源，写入和检测请求需要页面令牌。不是公网多用户服务。安装、服务管理及可执行文件查找见 [部署说明](docs/deployment.md)，渠道扩展见 [扩展契约](docs/channels.md)。

## CLI 排查

CLI 可以通过 `--app-workspace <UUID>` 或环境变量 `RUNNER_WORKSPACE` 使用 Web 中建立的工作区。UUID 可从浏览器 URL 的 `workspace` 参数获得。`--workspace` 仍指 TAPD 项目 ID，不是应用工作区 ID。

```sh
npm run tapd:search -- --app-workspace <UUID> --query 登录
npm run tapd:detail -- --app-workspace <UUID> --id <需求ID>
npm run tapd:task -- --app-workspace <UUID> --id <需求ID>
npm run tapd:status -- --app-workspace <UUID> --id <需求ID>
```

`tapd:task` 只下载图文和生成预览。`tapd:run` 执行真实需求，必须显式传 `--id` 且配置 `workflow.allow_write: true`；`tapd:retry-transition` 只修复已有执行的渠道状态。Web 不接受 `--config`；CLI 仍支持 `--config <文件>` 指定配置。已有运行记录不会再次自动启动。

## 验证

代码目录与模块依赖见 [模块与目录规范](docs/engineering/architecture.md)。后端按职责分层，前端按功能分组；测试分别位于 `test/architecture`、`test/unit`、`test/integration` 和 `test/browser`，运行命令保持如下。

界面沿用 C 方案，统一视觉规范见 [UI 设计契约](docs/engineering/ui-design.md)。全页面生图原型和提示词位于 `output/imagegen/unified-pages-20260917/`；运行 `npm run test:visual` 可生成纯模拟数据的桌面、平板和移动端实现截图，索引为 `state/browser/unified/index.html`。

```sh
npm run lint
npm test
npm run build
npm run test:web
npm run test:visual
# 一次运行上述全部检查
npm run verify
```

测试使用模拟 TAPD/Codex 和临时 Git 仓库，覆盖工作区隔离、同需求跨工作区执行、凭据维护/检测、需求模型选择、图片及 SSE 隔离、创建/切换/重命名、刷新和移动布局。不会执行真实需求或修改真实 TAPD。Windows 使用本机 Edge，Linux/macOS 使用 Playwright Chromium；截图在忽略的 `state/browser/`。

Windows / Linux 环境准备和双平台 CI 接入见 [平台验证说明](docs/engineering/platform-verification.md)。仓库提供可从 Gitee 检出的 Jenkins 流水线，两端分别安装依赖并运行同一套检查。
